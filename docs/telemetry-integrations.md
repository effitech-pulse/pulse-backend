# Интеграции телеметрии

Модуль подключён к `/api/v1/integrations` и `/api/v1/telemetry`. HTTP и OpenAPI
принадлежат backend; для скоринга используется существующий gRPC Upload
из pulse-contracts. Контракты модели не копируются и не изменяются.

## Запуск

1. Укажите `DATABASE_URL` и примените схему явно: `make migrate`.
   Миграция добавляет telemetry_source, telemetry_source_profile,
   telemetry_measurement и telemetry_collection_log; существующие таблицы не пересоздаёт.
2. Укажите `INTEGRATION_ALLOWED_HOSTS`: точные имена серверов источников.
   Пустой список запрещает исходящие подключения. Перенаправления HTTP не выполняются.
3. Для сохранения токенов/паролей задайте `INTEGRATION_SECRET_KEY` — 32 случайных
   байта, закодированных base64. Ключ хранится отдельно от БД и должен сохраняться
   между перезапусками. В БД записывается AES-256-GCM шифротекст; API его не возвращает.
4. Запустите `make run`. Источники создаются как черновики; запуск — отдельный PATCH.
   При ошибке повторный сбор выполняется через минуту. PostgreSQL lease предотвращает
   одновременный сбор одного источника несколькими API-процессами.

Для промышленного доступа задайте существующий `API_KEY`. Секрет в интерфейсе
передаётся только при изменении: отсутствие поля сохраняет прежнее значение,
пустая строка удаляет секрет. Пароли в URL запрещены. Каждое сохранение настроек
создаёт неизменяемую версию профиля без секретов.

## Источники

- JSON pull: GET адреса с `since` (ISO 8601 UTC). Токен передаётся как Bearer.
  `records_path` выбирает массив объектов. Сервер источника должен фильтровать
  измерения по `since`. Время измерения — RFC 3339 с часовым поясом.
- JSON push: `POST /api/v1/integrations/{id}/ingest`, тело `{"records":[...]}`.
  Источник должен иметь kind=json_push и status=running. Авторизация — X-API-Key.
- PostgreSQL: адрес `postgresql://reader@host:5432/database?sslmode=verify-full`.
  Пароль задаётся отдельно. Чтение в транзакции read-only.
- MySQL: `mysql://reader@host:3306/database`. TLS включён по умолчанию;
  `?tls=false` допускается только для локального стенда без TLS.
- ClickHouse: HTTP/HTTPS endpoint, например `https://host:8443/?database=production`.
  Имя пользователя допускается в URL, пароль задаётся отдельно; запрос readonly=1.

Для БД указываются table_name, time_field, well_field и mappings. Таблица и колонки
проверяются как идентификаторы, значения передаются параметрами. Произвольного SQL
в интерфейсе нет. JSON-столбцы PostgreSQL допускают вложенные пути сопоставления.
Идентификатор из источника хранится без потери int64. В карточках и ручных
файлах интерфейса используется ID Pulse; тип внешнего ID задаётся в профиле. Телеметрия открывается в `/wells/{id}?tab=telemetry`.
Маршрут `/telemetry/{ID Pulse}` перенаправляет в существующую карточку.
Новый ID в измерении не создаёт скважину автоматически.

Первый pull читает последние 24 часа; последующие — от подтверждённого времени
измерения с перекрытием в минуту. Начальную историю можно импортировать файлом.
Ограничения текущего этапа: до 10000 записей и 8 МиБ ответа за цикл. Если окно БД
превысило лимит, оно отклоняется целиком: нужен более узкий источник/представление.
Постраничная догрузка больших архивов — отдельное расширение; превышение лимита
не считается успешным сбором и не продвигает позицию.

## Проверка, хранение, скоринг

Маркеры изоляции 9999 и реактивной энергии 9999/999.9 очищаются до преобразования
единиц (допуск 1e-6). Ноль не является пропуском. Уставки исключаются из измерений.
Плохие ID/время отклоняются и учитываются в журнале. Модель не обучается на новых
данных автоматически; temporal/group/purge протоколы обучения не меняются.

Сохранение измерений, итог цикла и подтверждение позиции выполняются транзакционно.
Ключ дедупликации — well_id + measured_at. При конфликте остаётся прежняя запись;
автоматического исправления и слияния разных наборов каналов в одном timestamp нет.
Итоги доступны в журнале, секреты туда не попадают.

`POST /telemetry` принимает канонический пакет points для подтверждённого импорта.
До 100000 записей, HTTP-тело до 4 МиБ. Для больших файлов разбейте импорт на части.
`GET /telemetry?well_id=...&start=...&end=...` возвращает максимум 10000 записей
и явный truncated=true при превышении. Период ограничен 366 днями.

`POST /telemetry/score` принимает well_id/start/end, формирует CSV из полной выборки
и вызывает существующий ML Upload. Недостаток истории обрабатывает ML-сервис.
Это разовая проверка периода: она не изменяет ярус и статусы тревог фонда.
Автоматический пересчёт модели после каждого цикла сбора пока не включён.

## Проверки

`make check build` и `TEST_DATABASE_URL=... make integration`.
Интеграционные тесты используют отдельную БД и временные схемы с очисткой:
повторная миграция, версии профиля, JSON push/pull, lease, повторы, пауза,
сохранение нуля/null и текстового int64, атомарный импорт.
Живые ClickHouse/MySQL заказчика в тестах не используются.

## Pulse Data и существующий архив

`TELEMETRY_DATA_API_URL=http://127.0.0.1:8092` подключает JSON API Pulse Data.
Этот хост также должен входить в `INTEGRATION_ALLOWED_HOSTS`.
`GET /telemetry/bounds?well_id=...` возвращает границы доступной истории;
интерфейс выбирает последний доступный архивный период.

Pulse Data использует проверенную карту `device_id` (Unitek) → `well_id`
ClickHouse из отчёта аудита и повторно фильтрует оба ID в каждом запросе.
Реестр приложения и архив имеют разные первичные ключи. Доступ к CH read-only.
Маркеры из общего `esp.rules.config.MarkerConfig` очищаются до argMax.
Часовая сетка содержит последнее событие каждого канала внутри часа, без ffill;
метка — правая граница бакета, разрешение указано в ответе. Это обзорная выборка,
не исходная секундная телеметрия и не подтверждение качества диагностики FAST.

Архивные и собранные точки объединяются по времени; при точном совпадении
приоритет имеет сохранённая точка. Ошибка архива возвращается явно.
Для скоринга существующая модель требует не менее 30 суток измерений.

Показательный фонд генерируется в `pulse-data`, подключается обычным JSON pull
с `records_path=points`. ID -900000..-900099 выделены для 100 скважин; сценарии
15 деградирующих установок хранятся отдельно от входа модели. Команда
`python -m scripts.connect_telemetry_fleet --api <URL>` регистрирует фонд
идемпотентно и запускает источник. Для показа используйте отдельную БД того же
приложения. В карточке показательной скважины выводится одно уведомление NDA.
Генерация не назначает риск и не гарантирует обнаружение 15 сценариев моделью.


## Внутренний ID Pulse и связи с источниками

Основной идентификатор — существующий `well.id`, автоматически назначаемый
PostgreSQL. `unitek_id` и `armits_id` стали nullable (явная миграция 3), их
прежние значения и ограничения уникальности сохранены. Создание скважины
требует НГДУ и цех, внешний ID необязателен. Поле id нельзя назначать через POST.
PATCH с null отключает соответствующую связь; отсутствие поля её сохраняет.

Интерфейс использует `/wells/{ID Pulse}/telemetry`, `/telemetry/bounds` и
`/telemetry/score` внутри того же префикса скважины. В ответах измерений well_id
содержит ID Pulse. `POST /api/v1/telemetry/import` также принимает ID Pulse;
импорт хранится под внутренним ключом pulse:{id}, который не пересекается
с числовыми идентификаторами прежних источников. При отключении связи эти
измерения сохраняются. Историческая запись источника читается по его связи.
`/wells/{ID Pulse}/risk` и `/risk/history` разрешают связь с исследовательским
ML-ID на сервере; frontend её не вычисляет.

Профиль источника имеет well_identity: pulse / unitek / armits. Новые профили
интерфейса используют pulse. При заданном типе весь пакет сопоставляется со
справочником и хранится под ID Pulse. Несопоставленный ID отклоняет пакет без
продвижения позиции. Старые профили без этого поля и прежние /telemetry API
сохраняют контракт для совместимости с настроенными интеграциями.

Экспорт реестра `GET /wells/export?identity=pulse` содержит PULSE_ID, WELL_NUMBER,
NGDU, CEX. Старый формат экспорта остаётся без query-параметра. В bulk/XLSX
импорте id/PULSE_ID существующей скважины означает пропуск строки, без изменения
карточки и без дубля. Неизвестный ID Pulse отклоняется; для создания новой
скважины поле нужно оставить пустым.


## Сохранённые ручные проверки

В карточке скважины вкладка «Телеметрия» → меню «⋯» → «Проверить моделью» запускает расчёт выбранного полного периода от 30 суток. Результат доступен во вкладке «Проверки» и по ссылке `?tab=checks&check=<id>`. Проверка привязана к внутреннему ID Pulse; смена внешних связей не меняет историю.

`POST /api/v1/wells/{well_id}/checks` принимает start/end в RFC3339 (точность до микросекунды) и request_id (16–80 ASCII букв, цифр, `_`, `-`). Повтор того же request_id и периода возвращает сохранённый результат без скоринга. Использование ключа с другим периодом даёт 409. Одновременные первые запросы могут выполнить расчёт дважды, но уникальный ключ в PostgreSQL оставит единственную запись. Для нового осознанного расчёта нужен новый request_id.

`GET /api/v1/wells/{well_id}/checks` возвращает до 25 проверок; `before=<last_id>` открывает следующую страницу. `GET /api/v1/wells/{well_id}/checks/{id}` возвращает сохранённый ответ: временной ряд риска, вклады SHAP, период, число точек, дискретность и SHA256 точных CSV-байтов, переданных модели. Модель передаёт имя и SHA256 комплекта meta/model/calibrator/normalizer/drift; версия относится к контексту, использованному в расчёте. Если старый ML-сервис не передал версию, она остаётся null.

Запись неизменяема. Исходная телеметрия не копируется: отпечаток позволяет сверить вход, но не восстановить изменённые данные источника. История содержит ответы ML, включая «недостаточно данных»; сетевые ошибки не создают успешную проверку. Закрытие вкладки не отменяет выполняющийся запрос (лимит 5 минут плюс 10 секунд на запись); остановка серверного процесса прерывает незавершённый расчёт. Постоянного фонового задания и автоматического перезапуска нет. Клиент сохраняет request_id для повторной отправки после таймаута.

Миграция №4 выполняется явно через `make migrate`; при старте API схема не меняется. Сохранённые проверки блокируют физическое удаление скважины и сохраняют её историю. Автоматический запуск ML, изменение яруса и создание тревог из ручной проверки не выполняются. Загрузка файла на отдельной странице `/upload` пока остаётся отдельной разовой проверкой; история здесь относится к телеметрии выбранной скважины.


## Обработка результата технологом

Миграция №5 добавляет единый процесс для сохранённых проверок и тревог фонда: ответственный (вводимое имя), статус «новая / в работе / завершена», заключение «подтверждено / не подтверждено / нужны дополнительные данные» и комментарии. Завершение требует ответственного и обоснования. Повторное открытие требует причины, предыдущие заключения сохраняются в событиях.

Для проверки используются GET/PUT `/api/v1/wells/{well_id}/checks/{id}/review`, для тревоги — GET/PUT `/api/v1/ml/alerts/{id}/review`. PUT содержит revision и request_id. При устаревшей версии — 409, форма не перезаписывает чужие изменения. Повтор того же ключа и тела не добавляет событие; изменённое тело с тем же ключом отклоняется. История выдаётся по 50 событий; before=revision открывает предыдущую страницу. Каждое событие содержит предыдущие и новые значения, автора и время.

Состояние, событие и статус ml_alert пишутся одной транзакцией. Совместимый PATCH статуса тревоги также записывает событие с пометкой о совместимом API. Подтверждённое заключение соответствует статусу confirmed, неподтверждённое — false_positive, запрос дополнительных данных — inconclusive. Назначение в работу не считается окончательной проверкой в показателях обратной связи ML: denominator alerts_reviewed включает только confirmed и false_positive. Исследовательские метрики модели не меняются. Обработка не меняет риск или ярус фонда.

Пока используются локальный сеанс или общий API-ключ, автор события явно имеет authenticated=false. Вводимое имя ответственного не доказывает авторство и не предоставляет доступа. События не принимают имя автора из тела запроса. Персональные роли и ограничения фонда подключаются отдельным этапом.


## Рабочий и показательный фонды

Миграция №6 добавляет well.fund_type: operational (по умолчанию) или presentation. Флаг не заменяет авторизацию и не меняет внешние связи. Исторический выделенный диапазон -900099…-900000 с НГДУ/цехом -900 принимается как показательный. Обычные скважины не переклассифицируются. Тип задаётся при создании, не меняется обычным PATCH.

GET /wells?fund=operational|presentation фильтрует реестр, тот же параметр доступен для экспорта. Отсутствие параметра сохраняет прежний ответ по всем фондам. Переключатель в приложении меняет видимый фонд; карточка скважины синхронизирует выбор с собственным типом фонда.

GET /presentation/summary возвращает активные показательные скважины и последнюю сохранённую ручную проверку каждой. Счётчики watch/alert/insufficient вычисляются из этих ответов; ни сценарии генератора, ни оценки рабочего фонда не подставляются. GET /presentation/scenario читает метаданные только у настроенного Pulse Data (TELEMETRY_DATA_API_URL и существующий allowlist).

Сценарий содержит 100 обезличенных скважин и 15 вариантов деградации. Это запланированная динамика входа, а не 15 гарантированных обнаружений модели. Исследовательские метрики и автоматические ярусы сюда не переносятся. Модель запускается кнопкой «Проверить месяц», результат попадает в обычную историю скважины.

## Этап 4 — персональный доступ и будущий SSO

Режим `AUTH_MODE=local` включает серверные сеансы и роли: `admin`, `technologist`,
`viewer`. Роль хранится в Pulse и не принимается из заголовков, JSON клиента или
внешних claims. Scope пересекает доступные фонды, НГДУ и цеха. `null` означает все,
пустой массив — ни одного; коды `0` и отрицательные коды сохраняются. Списки,
экспорт, карточки, телеметрия, сохранённые проверки и объяснения ML ограничены тем
же scope. Несопоставленный внутренний ID ML недоступен ограниченной роли.

Технолог запускает ручную проверку разрешённой скважины, оформляет обработку и
добавляет инцидент. Наблюдатель читает данные. Изменение справочников, интеграций,
глобальный прогон ML, общий аудит и исследовательские метрики доступны
администратору. В истории заключений фиксируется серверный ID и имя пользователя.

Миграция 7 создаёт `auth_user`, `auth_session`, `auth_identity`. Первый администратор
создаётся **только** серверной командой `bin/adminuser -login LOGIN -name NAME`:
пароль передаётся одной строкой через stdin, не через argv или переменную среды.
Команда откажет, если пользователи уже существуют. Пароль не короче 15 символов,
не длиннее 72 байт UTF-8; хранится bcrypt-хеш. После создания включите
`AUTH_MODE=local`, настройте точные `CORS_ORIGINS` и перезапустите API.
`AUTH_COOKIE_SECURE=true` обязателен для HTTPS; на локальном HTTP задайте `false`.
Установка `local` не создаёт пользователя и не включает саморегистрацию.
В текущем рабочем экземпляре сохранён `legacy`, реальные учётные данные не созданы.

Сеанс живёт 8 часов, случайный токен передаётся только в HttpOnly SameSite=Strict
cookie; в БД хранится SHA-256 токена. Изменение аккаунта отзывает все его сеансы;
роль/scope читаются с сервера при каждом запросе. Защищены конфликт версии и
последний активный администратор. Есть ограничение частоты входа. Мутации через
cookie проверяют Origin. При истечении сеанса интерфейс очищает кеш данных.
Общий `X-API-Key` не обходит персональные роли в режиме `local`: интеграционные
push-клиенты потребуют отдельного сервисного механизма; pull-сборщик работает
внутри backend независимо от пользовательского сеанса.

Будущий Keycloak/OIDC адаптер должен выполнить discovery, проверку issuer,
подписи, audience, nonce/state и PKCE на сервере, затем вызвать
`Access.AcceptIdentity` с проверенными `provider_id` и `subject`. Связь с
`auth_user` хранится отдельно; совпадение email не связывает пользователей
автоматически. `BindIdentity` доступен только доверенному администраторскому
сценарию; публичного endpoint для непроверенного subject нет. Выданный сеанс и
права едины для локального и будущего внешнего входа. Сам протокол OIDC, настройки
провайдера и автоматическая регистрация пока **не реализованы**. Стабильный
provider_id должен однозначно соответствовать одному issuer и не переназначаться.

API: `GET /auth/me`, `POST /auth/login`, `POST /auth/logout`,
`GET/POST /auth/users`, `PUT /auth/users/:id` (пути с префиксом `/api/v1`).
Администраторский экран `/accounts` управляет именем, ролью, scope, активностью,
сбросом пароля и revision. Пароли и токены отсутствуют в списке пользователей.

## Этап 5 — единая выборка фонда

Обзор фонда, список скважин и экран рисков используют единый контекст:
фонд, НГДУ, цех, поиск по ID Pulse/номеру и сортировку по ID/номеру.
Выбор сохраняется локально отдельно для пользователя и каждого фонда,
восстанавливается после переходов и перезагрузки. Фильтры не заменяют серверный
scope: они только сужают разрешённую выборку. Справочники в панели содержат
доступные в этом фонде коды. Ноль и отрицательные коды не трактуются как «все».

`GET /wells`, `/wells/export`, `/incidents/stats` поддерживают `fund`, `ngdu`,
`department`, `search`, `sort` (`id_asc`, `id_desc`, `name_asc`, `name_desc`).
Экспорт повторяет условия и порядок списка, включая `active_only`.
Для статистики считается история выбранных скважин, включая неактивные;
агрегация выполняется в БД по списку разрешённых Pulse ID. Поиск не использует
идентификаторы сторонних систем. Короткий поиск — подстрока, а не точный ID.
Таблица показательного фонда и её счётчики следуют тем же фильтрам; информация
о сценарии генератора описывает сценарий целиком и остаётся отдельным блоком.
Контекст выбранных фильтров пока хранится в браузере, без синхронизации между
устройствами и без включения в URL.

## Этап 6 — архив и история карточки

Архив — отдельный `archived_at`, независимый от `active`. Скважина сохраняет ID
Pulse, связи, телеметрию, инциденты, проверки и заключения. Архив скрыт из текущих
списков, текущей статистики и списка рисков; вычисленный ярус не сбрасывается.
Исторические ответы модели и телеметрия доступны в карточке архива. Архивирование
не выключает внешний источник: его поток может обслуживать много скважин.

Миграция 8 добавляет `well.revision` (исходно 1), `responsible`, `archived_at` и
`well_event`. Изменение метаданных, архивирование и восстановление блокируют строку
скважины и атомарно записывают новую версию вместе с событием до/после и автором.
История начинается с изменений после миграции; прошлые действия не выдумываются.
Ответственный — текстовое имя, не предоставляющее роли или доступ.

`POST /wells/:id/archive` и `/restore` принимают `{revision, reason}`. Причина
обязательна, до 1000 символов. Управление архивом и реквизитами — администратору;
чтение архива/истории — по обычной области доступа. Устаревшая версия даёт 409,
данные не перезаписываются. Изменять реквизиты архивной карточки нельзя до
восстановления. `GET /wells/:id/history?before=REVISION` возвращает до 50 событий
по убыванию версии; добавлять/править события через API нельзя.

В `AUTH_MODE=local` PATCH требует `revision`; в legacy старые клиенты могут
опустить её, но каждая запись также увеличивает версию и создаёт событие.
Прежний DELETE теперь архивирует и возвращает 204. В local он требует `If-Match`
с текущей версией; в legacy повторный DELETE уже архивной записи идемпотентен.
Обычный GET архивной карточки даёт 404, явный `include_archived=true` открывает её.
Приложение использует явные archive/restore и передаёт версию на всех формах.

Параметр списка, экспорта и статистики `archive=current|archived|all` по умолчанию
равен current. Фильтр `active_only` сохраняет прежнее значение флага активности;
интерфейс при показе архива/всех включает и неактивные записи. Экспорт с
`identity=pulse&lifecycle=true` добавляет ACTIVE, ARCHIVED_AT, RESPONSIBLE, REVISION
после четырёх прежних колонок. Без lifecycle=true прежний формат не меняется.
Повторный импорт существующего ID Pulse пропускается и не восстанавливает архив.
