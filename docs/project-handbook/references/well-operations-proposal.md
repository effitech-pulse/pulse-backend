# Паспорт установки, эксплуатация и помощник — предложение, 20.10.2026

**Новое требование, рассматривается. Реализация не назначена.** Источник — пользовательский запрос о характеристиках установки и назначении скважины, работах/заменах, отчётах и графиках, ролевом доступе, действиях сотрудников и навигационном ИИ-помощнике в образе мини-робота в каске. Это отдельная продуктовая постановка; текущий порядок [O2→Q0→Q1/F2](functional-roadmap.md) сохраняется. Научная ML-приёмка user-deferred/not_assessed.

**Уточнения пользователя:** источник паспорта и истории работ пока неизвестен; нужны **загрузка и выгрузка Excel** (последнее явное уточнение пользователя). Для загрузки ниже предложен отдельный сценарий шаблон→preview→валидация→явное сохранение паспортов/работ; это не импорт телеметрии или реестра скважин. Первый график — существующие суточные факт/ожидание дебита. MongoDB предложено **рассмотреть по уместности**, без выбора БД/установки. Реализация нового блока не назначена.

**Архитектурная сверка завершена:** [выводы и источники](well-operations-data-review.md), [current/proposed C4](../diagrams/well-operations-proposed.drawio). Для первой версии рекомендован существующий PostgreSQL: связи, интервалы и работы в таблицах; вариативные паспортные атрибуты — в ограниченном versioned JSONB. Доказанной необходимости второй БД пока нет; условия пересмотра MongoDB приведены в сверке. Это предложение для согласования, установка БД не проводилась.

## Пользовательский результат

Технолог открывает скважину и понимает, для чего она используется, какая установка действовала в выбранный момент, откуда взяты характеристики и что неизвестно. Он видит подтверждённые работы/замены и может сопоставить их с эксплуатационным состоянием и графиком известных измерений. Уполномоченный сотрудник загружает Excel паспортов/работ, видит распознанные сущности, изменения и ошибки до сохранения; выгружает разрешённый отчёт в Excel. Руководящий доступ не предполагается автоматически: отчёты и персональная аналитика доступны только по серверным правам. Сотрудник получает понятную помощь по доступным ему действиям и текущим инструкциям.

Варианты рассмотрения: один большой экран с произвольными полями быстро смешает паспорт, телеметрию и ремонт; полная интеграция с неназванной внешней системой преждевременна. Предлагается поэтапная модель с явным происхождением/временем и отдельными вертикальными сценариями. Это рекомендация техлида, не согласованные поля/источники/дизайн.

## Подтверждённая база и пределы

В Well (исходник `pulse-backend/internal/domain/models.go`; в пакет не включён) есть Pulse ID, внешние IDs, active, fund_type, responsible, revision и archived_at. WellEvent (исходник `pulse-backend/internal/domain/well_lifecycle.go`; в пакет не включён) содержит actor, before/after и revision: это история административного lifecycle, а не доказанный архив ремонтов или паспорт оборудования. В local access (исходник `pulse-backend/docs/telemetry-integrations.md`; в пакет не включён) описаны viewer/technologist/admin и серверная session identity; новая manager role не вводится. AuditEntry в модели содержит method/path/status/actor: HTTP-статус сам по себе не доказывает committed бизнес-результат и не является полной usage analytics.

Пользователь выбрал существующие суточные факт/ожидание дебита для первого графика. Последующая архитектурная сверка кода pulse-data установила: `qg` и `qg_tex` — факт/ожидание дебита жидкости, м³/сут; `qn` — нефть, т/сут. Реальные coverage, единицы каждого источника, правила коррекции и привязка к Pulse ещё требуют проверки. Готового daily API в проверенном backend не найдено; соединять разные БД по одноимённому `well.id` нельзя. Нет оснований придумывать паспортные характеристики или backfill истории.

## Предлагаемая предметная модель

| Понятие | Значение и границы |
|---|---|
| WellPurpose | Назначение скважины: добывающая/нагнетательная/unknown, с периодом действия и источником. Оно независимо от типа насоса и административного фонда. Уточнить смешанное назначение/перевод и историю. |
| Equipment / EquipmentType | Идентифицируемая установка и её тип/модель, название, паспортные характеристики с единицами и provenance. Неизвестные значения — unknown/null, не ноль. Состав агрегата/серийные номера и обязательные поля определяются по реальному паспорту. |
| EquipmentAssignment | Временная связь установки с Pulse well ID: valid_from/valid_to, источник, revision; замена закрывает прежнюю связь и открывает новую, не переписывая прошлое. Правило эксклюзивности/пересечений и допустимость комплекта из нескольких единиц фиксирует архитектор. |
| Частота | Nominal — паспортная; allowed — допустимый диапазон с источником/периодом; setpoint — уставка; actual — измерение с timestamp/качеством. Ни одна не выводится автоматически из другой. F_out=0 может быть валидным простоем; отсутствие датчика не означает ноль. |
| OperatingState | operating/repair/idle/unknown на момент/интервал времени. Это не active/archived. Источник может быть подтверждённым событием или отдельно обозначенным расчётом по телеметрии; конфликт не скрывается. |
| WorkRecord | Тип работы/замены, planned/started/completed/cancelled, интервалы план/факт, ответственные, связанное оборудование/назначение, источник и server revision. Коррекция сохраняет происхождение/историю; свободный комментарий не заменяет структурированное событие. |

Новая purpose/equipment identity не включает автоматически скважину в существующий ML recipe. Нужна отдельная проверка применимости, каналов и границ обучения; unsupported/unknown показываются явно. Риск/ярус/качество данных/решение технолога остаются независимыми.

## Загрузка Excel: предлагаемый небольшой сценарий

Загрузка и выгрузка теперь подтверждены пользователем; **источник достоверных паспортов/работ по-прежнему неизвестен**. Файл — способ передачи утверждений, не доказательство их достоверности. До enable нужны source owner, разрешённое происхождение/ручное внесение, поля и correction policy. Первый рекомендуемый формат — versioned XLSX без макросов; поддержка старого XLS/прочих форматов отдельно OPEN. Report workbook и import template могут иметь разные схемы: произвольный отчёт не обещает безопасный round-trip.

Предлагаемый первый slice: получить шаблон → выбрать одну существующую разрешённую Pulse well → загрузить одну паспортную revision → серверный bounded parse/сопоставление → preview изменений и ошибок → явное подтверждение → транзакционный commit и receipt → повторно открыть паспорт/историю. Следующий малый slice использует тот же контролируемый flow для одной работы/замены с interval/revision rules WO-P1. Entity scope (включая equipment identity/assignment/purpose), точные колонки, единицы и интервалы утверждаются архитектором/владельцем источника; шаблон не принимает любые поля Well.

Идентичность сопоставляется через explicit Pulse ID и согласованный external namespace/key; несовпадение/неоднозначность не разрешаются совпадением номера скважины или одноимённых DB IDs. Неизвестное оборудование может создаваться только по принятому entity/source контракту; чужие скважины не создаются. Пустая ячейка не стирает действующее значение по умолчанию; clear/correction — явная команда с revision/reason. Номинальная/допустимая частота не берётся из actual, active не становится repair, исторический performer не подменяется uploader.

Сервер связывает commit с immutable preview snapshot и его schema/template/parser/mapping versions, fingerprint, expected revisions; mutable preview или изменённый после validation файл требуют нового preview. Транзакционная единица первого slice — одна bounded предметная команда. Для будущего batch архитектор отдельно закрепляет all-or-nothing либо explicit independent accepted commands/receipts; молчаливая partial success запрещена. Дубликат проверяется после текущей авторизации; history сохраняет source/recorded_at/actor, claimed historical performer и valid-time/precision отдельно. Удаление/замена прошлого только через принятые corrections; файл не является разрешением backfill.

Предлагается отклонять formulas (включая cached results), macros и external links, не вычислять формулы и не выполнять внешние обращения. IDs в шаблоне текстовые; потерянная Excel precision не восстанавливается догадкой. Date format/Excel epoch/timezone/calendar policy явные; неоднозначность даёт error до commit. Архитектор задаёт измеряемые import/export quotas, ZIP/row/cell/memory/time/temp/concurrency caps, cleanup и retention частных файлов/preview; числа Q0/Upload автоматически не наследуются. Синтетический plan/evidence возможен до реальных источников, реальные файлы не загружаются этой постановкой.

## MongoDB и PostgreSQL: первичные источники для архитектурной оценки

Прочитано 20.10.2026: MongoDB Manual (текущая документация, **не выбранная версия установки**) и PostgreSQL **16**. Ниже факты документации; применение к Pulse в соседней колонке — вопросы/выводы техлида для проверки архитектором, не решение о БД и не benchmark.

| Проверенный факт | Значение для сравнения Pulse |
|---|---|
| MongoDB поддерживает embedded documents и references. Документация рекомендует учитывать совместное чтение/обновление; для неограниченно растущих вложенных данных и высококардинальных children рассматривает references. [Data modeling](https://www.mongodb.com/docs/manual/data-modeling/best-practices/) | Паспорт как ограниченный документ — кандидат для embedding; многолетние работы/назначения/employee facts нельзя автоматически складывать в бесконечный массив одной скважины. Нужны реальные размеры и access patterns. |
| В MongoDB можно задавать schema validation типов/диапазонов; по умолчанию невалидная вставка/обновление отклоняется, но существует настройка warning. [Schema validation](https://www.mongodb.com/docs/manual/core/schema-validation/) | «Гибкий паспорт» всё равно требует versioned schema, обязательных единиц/source/revision и политики invalid records. Утверждение «MongoDB без схемы» не является основанием выбора. |
| MongoDB имеет atomic single-document writes и multi-document transactions, в том числе для replica sets/sharded clusters; read/write concern влияет на guarantees. [Transactions](https://www.mongodb.com/docs/manual/core/transactions/) | Сверить транзакционную границу «закрыть старое назначение + открыть новое + committed факт» и нужную deployment topology. Наличие транзакций не выбирает boundary и не доказывает восстановление Pulse. |
| MongoDB aggregation pipelines фильтруют/группируют документы; `$lookup` выполняет left outer join с коллекцией той же БД. [Aggregation](https://www.mongodb.com/docs/manual/aggregation/), [$lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/) | Scoped отчёты возможны как предмет оценки; проверить ACL до aggregation и внутри связанных выборок, interval joins, distinct wells, Excel totals и индексы. Нельзя обосновывать отказ от MongoDB отсутствием joins/aggregation. |
| PostgreSQL16 хранит JSON/JSONB; JSONB поддерживает GIN для определённых key/existence/containment/jsonpath запросов, причём operator class и выражение запроса имеют значение. JSONB не сохраняет исходные пробелы, порядок ключей и дубли ключей. [JSON types/indexing](https://www.postgresql.org/docs/16/datatype-json.html#JSON-INDEXING) | Сравнить normalized well/equipment/assignment/work/actor relations с JSONB для вариативных паспортных атрибутов в существующей БД. Если нужен точный исходный паспорт, JSONB не заменяет сохранение оригинала. GIN не объявляется универсальным ускорителем всех отчётов. |

**Критерии решения WO-A:** границы атомарности/revision/conflict и исторических интервалов; вариативность паспортных схем; scope до joins/count/export; рост history/usage и query patterns; provenance оригиналов; migration/backup/restore/retention/access и эксплуатация второго store. Архитектор сравнивает оба варианта на одинаковых синтетических сценариях WO/UA AC и реальных известных ограничениях, затем рекомендует вариант с доказательствами. Источник паспортов пока неизвестен; ни размер коллекций, ни преимущество latency/стоимости, ни необходимость новой БД здесь не установлены. БД и deployment не меняются.
