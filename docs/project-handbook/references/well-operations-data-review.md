# Паспорт и эксплуатация: архитектурная сверка, 20.10.2026

**Архитектурная сверка и incremental Excel delta завершены; предложение для следующего согласования, не решение о внедрении.** Вход: [proposal](well-operations-proposal.md), TL reports `well-operations-tl-report.md` и `well-excel-tl-report.md`, последнее уточнение «Выгрузка и загрузка Excel». Очередь O2→Q0→Q1/F2 не меняется; научная ML-приёмка deferred/not_assessed. Источник паспорта/работ неизвестен, загрузка и выгрузка Excel требуются, первый график — существующие суточные факт/ожидание дебита. MongoDB рассмотрена без установки/выбора runtime. Робот в каске — будущий brief. Новое уточнение учтено без повторного общего source-аудита.

## Предварительный вывод

Рекомендация для первой версии — существующий PostgreSQL: нормализованные identity/интервалы/работы/события и ограниченный versioned JSONB для вариативных паспортных атрибутов. Это вывод по существующим связям и транзакциям, не по измеренной скорости. MongoDB остаётся альтернативой для автономного каталога документов, если реальный источник и access patterns докажут пользу, превышающую стоимость второй БД и межбазовой согласованности. Benchmark и production volumes не установлены.

Паспорт не расширяет автоматически применимость ESP recipe к нагнетательной скважине. Active/archived, эксплуатационное состояние, риск, качество данных и решение технолога независимы. HTTP audit, click/attempt и committed бизнес-результат также различны.

## Первый график: найденный сквозной разрыв

pulse-data loader (исходник `pulse-data/utils/loaders/load_flow_postgres.py`; в пакет не включён) и его [PG DDL](../schemas/postgres/research-init.sql) описывают `measurement`: `qg` — фактический дебит жидкости, `qg_tex` — технологический/ожидаемый дебит жидкости, оба м³/сут; `qn` — нефть т/сут. `dat_zam` преобразуется в calendar date, `si_nam` — source. UPSERT по `(well_id, measured_at, source)` обновляет прошлые значения; истории редакций/времени доступности каждой ревизии нет. Несколько sources за сутки допустимы. Это подтверждение семантики кода, не проверка реальных книг, coverage или правильности единиц каждого файла.

Backend local Compose указывает app БД `esp_app`; её well schema (`ngdu/department`) отличается от data well (`ngdu_id/cdng_id`). В checked backend routes/domain/repository нет отдельного `qg/qg_tex` daily interface. frontend channel (исходник `pulse-frontend/src/lib/telemetry.ts`; в пакет не включён) содержит `Flowrate for current day`, но не доказывает тождество с ARMITS qg/qg_tex. Запрещён неявный join между одноимёнными `well.id` разных БД.

Следующий design slice сначала подтверждает путь `Pulse well → approved external ARMITS identity → data well → measurement`; отсутствующий/неоднозначный mapping даёт unavailable/unknown. Узкий read-only adapter возвращает `measurement_date`, series kind=`actual/expected`, quantity=`liquid_rate`, unit, source identity, coverage/quality и дату получения данных. Date не выдаётся за UTC timestamp без timezone/calendar policy. Несколько источников за дату показываются отдельно либо выбираются по согласованному правилу, не суммируются. Ожидание не является ML prediction. `0` остаётся 0, null — разрыв. Нельзя суммировать rate в объём или смешивать qn с qg. Новый KPI/исторически воспроизводимый export блокируется, пока не согласованы источник и correction policy. Простой read-only график не требует паспорта, MongoDB, broker или ИИ.

## Предлагаемые доменные правила для согласования

| Понятие | Предлагаемый контракт; OPEN |
|---|---|
| Назначение well | `producer/injector/unknown` — временное назначение, независимо от типа оборудования и administrative fund. Перевод producer→injector закрывает период, а не меняет прошлое. Mixed purpose/прочие типы OPEN; не кодировать их в active. |
| Оборудование и паспорт | Equipment identity отличается от EquipmentType/model. Состав установки — assembly/slot при реальной необходимости; serial number nullable, не глобальный ID без правила источника. Паспортная revision имеет schema version, source reference, recorded_at, valid period/precision, quality и typed attrs с единицами. Неизвестный паспорт не получает фиктивный manual source. Оригинал/его hash и права хранения согласуются отдельно; JSONB не заменяет оригинальные bytes. |
| Назначение оборудования | Известный интервал `valid_from, valid_to)`, открытый конец означает продолжающееся подтверждённое назначение; `end>start`. Unknown start не превращается в −∞: отдельная date precision/unknown representation, без утверждения действия на любое as_of. Для одного primary slot в well запрет пересечений; состав из нескольких slots допускает одновременность. Если оборудование физически неделимо, запрет назначения его в две well в одно время. Slot taxonomy и правило ретроспективных corrections OPEN. |
| Частота | nominal/allowed относятся к паспорту/revision и имеют unit+источник; setpoint относится к управляющей настройке с временем; actual — измерение с timestamp/quality. F_out не заполняет nominal/allowed/setpoint. allowed диапазон `min≤max`, numeric finite, неизвестная unit запрещает сравнение. set_* и is_set не становятся measurement. |
| Эксплуатационное состояние | Использовать одно canonical `running/repair/idle/unknown` после согласования с TL (proposal называет running `operating`). Admin active/archive не участвуют в вычислении. F_out>порог даёт telemetry-derived running, F_out=0 не доказывает repair. Подтверждённый repair интервал и телеметрия могут конфликтовать: вернуть evidence/conflict, не скрытый precedence. Порог, freshness и правила precedence OPEN. |
| Работа/замена | WorkRecord имеет свой ID, well/assignment links, type/status, отдельно planned/actual interval, source, revision, created/recorded times. cancelled plan не создаёт repair; completed work может иметь нулевую длительность как отдельное instant event, но не как пустой assignment interval. Ответственный/исполнитель/кто внёс — разные роли. |
| Actor и corrections | `occurred_at`/valid time отличаются от `recorded_at`; actor изменения — server session, исторический исполнитель может быть unknown с source evidence. Shared/service actor остаётся shared/service, не подставляется текущий сотрудник. Append correction с supersedes/reason сохраняет исходное утверждение. Для отчёта «что действовало тогда» нужны effective `as_of` и `known_at` либо сохранённый revision/snapshot; одна valid-time колонка не гарантирует стабильное старое представление после corrections. |
| Headcount и длительность | Единица счёта distinct Pulse well, не records/assignments. На срезе denominator — разрешённые сейчас well ∩ выбранная cohort version ∩ согласованная membership на as_of. Отсутствующая история membership → явно current-membership basis или unknown, без выдуманного historical scope. Права всегда текущие; historical as_of не возвращает утраченный доступ. Для периода duration — длина объединения интервалов, обрезанных периодом, а не сумма works. Conflicting/unknown intervals показываются отдельно; правило превращения evidence в исчерпывающую partition OPEN. |

Сценарий-проверка: установка A до t, B с t — на t ровно одна primary assignment. Поздний документ меняет дату с t на t−1d; старый export сохраняет snapshot/revision basis, текущий historical view отмечает correction. Две работы внутри одного repair interval не увеличивают distinct count/duration; неизвестная дата или состояние не становятся нулём.

## MongoDB и PostgreSQL: факты отдельно от рекомендации

PostgreSQL16 закреплён в [data Compose (исходник `pulse-data/deploy/postgres/docker-compose.postgres.yml`; в пакет не включён); реальная server version отдельно не проверялась. Версия MongoDB не выбрана. Ниже использован factual appendix TL (modeling/validation/aggregation), а transactions/lookup/JSONB и interval constraint дополнительно сверены по official docs 20.10.2026.

| Подтверждённая capability | Применение к Pulse — архитектурный вывод, не benchmark |
|---|---|
| MongoDB поддерживает embedding и references; bounded совместно читаемые документы и growing children требуют разного моделирования. [Modeling](https://www.mongodb.com/docs/manual/data-modeling/best-practices/) | Паспортный snapshot подходит для document shape; бесконечный массив works/assignments/usage внутри well ухудшит locality изменения и затруднит независимую retention. References/отдельные коллекции остаются полноценным вариантом. |
| MongoDB имеет schema validation с выбранной enforcement policy. [Validation](https://www.mongodb.com/docs/manual/core/schema-validation/) | Versioned паспорт и единицы нужны при любом store. «Без схемы» не является преимуществом для этого домена. В PostgreSQL JSONB syntax/type не заменяет доменную validation. |
| MongoDB имеет atomic document writes и multi-document transactions на поддерживаемой topology; read/write concern задаёт guarantees. [Transactions](https://www.mongodb.com/docs/manual/core/transactions/) | Замена с двумя assignments и business event возможна в MongoDB при правильном design. Это не транзакция с существующей PostgreSQL well/review/scope. Нельзя обещать атомарную dual-write цепочку из наличия Mongo transactions. |
| Aggregation/$lookup поддерживают группировку и left outer join с коллекцией той же БД. [Aggregation](https://www.mongodb.com/docs/manual/aggregation/), [$lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/) | Mongo может строить scoped отчёты. PostgreSQL identity/ACL/cohort придётся доставлять/проверять отдельно; `$lookup` не является прямым join с PostgreSQL. Access policy нужна до count и внутри каждого lookup, а не после global totals. |
| PG16 JSONB индексируется, включая GIN для подходящих операторов; порядок/дубли ключей и исходные пробелы не сохраняются. [JSONB](https://www.postgresql.org/docs/16/datatype-json.html#JSON-INDEXING) | Нормализованные well/equipment/work/actor связи и вариативные attrs можно держать вместе. Targeted expression/GIN только под реальные predicates; не обещать ускорение всех query. Raw original отдельно при принятом требовании. |
| PG16 имеет tstzrange, GiST и exclusion constraints для non-overlap; сочетание scalar equality+range возможно с btree_gist. [Ranges](https://www.postgresql.org/docs/16/rangetypes.html#RANGETYPES-CONSTRAINT) | Запрет пересечений per well/slot и equipment можно выразить в БД. Расширение не установлено этой задачей; его допустимость OPEN. Альтернатива — сериализовать изменение под row lock существующего well/equipment и проверять интервалы в той же transaction, с concurrency test. Только application pre-check без lock недостаточен. |

| Поток | Исходный вариант PG normalized+JSONB | MongoDB вариант / цена |
|---|---|---|
| Passport | equipment + passport revisions, bounded attrs JSONB; typed common units/identity | Документная revision удобна для разных каталогов, но сама вариативность не требует второго store. Реальные паспорта/частота whole-document updates неизвестны. |
| Assignment/work/repair | FK на Pulse well; атомарные close/open/correction/event; существующий pattern review tx | Referenced collections + transactions/serialization возможны; app FK и cross-store validity становятся обязанностью приложения. |
| Role/cohort report и Excel | Один scoped report module получает snapshot, export adapter форматирует тот же result | При Mongo primary catalogue + PG scope нужны согласованные версии/проекции. Отставшая ACL replica не может разрешать доступ; текущая server auth обязательна. |
| Daily flow | Узкий read adapter существующего measurement, explicit identity mapping; app/data БД уже различаются | Перенос в Mongo не устраняет неизвестный mapping, provenance и revision gap; добавляет copy/retention/reconciliation. |
| Protected usage/business events | Отдельные logical tables/access/retention; domain event в той же commit transaction. Append-heavy объём сначала измерить | Отдельная event collection возможна, но событие PostgreSQL commit требует durable delivery/outbox и дедупликации. Не добавлять broker только ради proposal. |
| Future help-assistant | Versioned allowlisted knowledge/context interface; storage выбирается по реальному corpus/search | Mongo сам по себе не решает ACL/RAG/prompt safety и не доказывает необходимость vector search/нового runtime. Curated help может обойтись существующими document resources. |

**Рекомендация:** сначала проектировать PostgreSQL в существующем backend, без универсального storage interface «на будущее». Один adapter означает hypothetical seam; второй реальный источник появляется только после подтверждения интеграции. Небольшой deep report module заслуживает interface: он концентрирует authorization, denominator, interval union, quality и snapshot metadata для UI/Excel. Deletion test: если удалить его, эта сложность размножится между HTTP/XLSX/assistant callers; его depth даёт leverage и locality. Напротив, отдельный паспортный microservice сейчас лишь переносит транзакционную сложность через сеть; необходимость автономного owner/deploy/scale не доказана.

**Стоимость второй БД:** отдельные backup/restore и совместимый recovery cut, upgrade/CVE/driver/version tracking, topology/TLS/credentials/least privilege, monitoring/on-call, quotas/retention, migration/reconciliation и эскалации ошибок. Если Mongo владеет паспортом, PG — membership/work, сначала определить единственного владельца каждого факта. Durable outbox+idempotent consumer, versioned projection, lag/status и reconciliation могут связать stores, но это eventual consistency, не одновременная атомарность. При частичном outage не выдавать mixed-version report за полный; показать unavailable/partial. Такие требования не вводятся в реализацию этим review.

**Условия пересмотра:** реальный authoritative источник document-native и имеет ограниченный автономный lifecycle; каталог преимущественно читается/меняется целиком; измеренные разнообразие/размер attrs, latency, contention или maintenance PG не удовлетворяют согласованным требованиям; команда принимает второй operational owner и проверенный restore/reconciliation. Сравнение на одинаковых репрезентативных данных: паспорт с несколькими schema versions, растущая history, concurrent replacement/correction, narrow/wide ACL, import preview/commit и export с совпадающим snapshot/receipt и denied scope. Измерять p50/p95 latency/throughput, RSS/temp, index/store/backup size, query plans, write contention, lag и restore time. Размеры и thresholds задавать после inventory, не выдумывать. Полный parity по 15 AC обязателен до performance вывода.

Polars/DuckDB сейчас не добавляют подтверждённой пользы: bounded operational report и XLSX уже находятся в Go/PG. Для большого offline analytical export их можно сравнить с SQL/существующим XLSX path на тех же source-approved snapshots по времени/RSS/temp/единицам/null/0, включая цену переноса ACL в ещё один engine. До профиля это не замена технологии и не задача установки.

## Interface/schema outline следующего согласования

**Target, не frozen API/DDL.** Изменения ограничить будущим backend HTTP → service → domain → repository/postgres; XLSX adapter без SQL. Frontend — consumer/server capabilities и Figma согласование, data — authoritative flow/source identity. Model не зависит от data; contracts/RPC не меняются для паспортов/Excel/help. Нужен отдельный совместимый контракт только если позднее согласуется ML applicability evidence.

Предложенные logical records: `equipment`, `equipment_passport_revision`, `well_purpose_revision`, `equipment_assignment`, `work_record` + immutable correction/event; при принятой privacy policy — `usage_event` отдельно от `business_event`. `well_id` ссылается на app Pulse ID; source reference/version, valid interval/precision, recorded_at, actor kind/account ID nullable, revision и quality типизированы. Core identity/units/interval/status/scoped predicates не прячутся в произвольный JSONB. Foreign source records имеют namespace/external key; уникальность source+key только при доказанной семантике источника.

Предложенные HTTP seams: `GET /api/v1/wells/{id}/operations?as_of&known_at`; paged history с stable cursor; `POST .../equipment-replacements` с request_id/expected_revision и одной атомарной командой close/open/work/event; work edits с optimistic revision; `GET /api/v1/operations/report?...` и отдельный export этого же snapshot/query contract; `GET .../daily-flow?from_date&to_date` с explicit date semantics. Имена/path/state vocabulary OPEN; не переиспользовать review endpoint для ремонта.

Response отчёта несёт report/schema version, snapshot/revision basis, generated_at, as_of либо period, timezone, cohort_version/membership basis, разрешённый фильтр, denominator definition, distinct counts/durations, unknown/conflict/coverage, source/version/unit и completeness. Scope вычисляется сервером из principal∩profile cohort до любых joins/aggregates. Фильтры только сужают; array well IDs/capabilities/actor от клиента не авторизуют. Cache key включает principal/policy/scope revision+cohort+as_of+query; account switch/revoke инвалидирует доступ. При невозможности зафиксировать current policy повторная проверка перед выдачей, явный отказ/перестроение вместо старого global cache.

Mutation: current capability/scope → well/target lock → idempotency key+canonical payload fingerprint → revision/interval validation → state+event+receipt commit. Same key/same payload возвращает сохранённый receipt первоначальной команды; изменённый payload →409, новый key/stale revision →409. Авторизация до duplicate lookup. Race две замены сериализуется; ошибка не оставляет «закрыто A, не открыто B». Unknown historical actor не влияет на session actor mutation. Нет автоматических повторов неидемпотентной команды без key.

Индексы-кандидаты: FK/lookup `(well_id, valid_from)`, `(equipment_id, valid_from)`, current slot uniqueness по принятой модели, history `(well_id, recorded_at, id)`, dedup command namespace+request key, approved source key; GiST/exclusion только после принятия interval policy, JSONB index только под approved predicates. `EXPLAIN ANALYZE`/concurrency/restore tests на изолированной БД обязательны перед enable, не на рабочей. Нет оснований переносить весь паспорт или telemetry JSON в GIN автоматически.

Migration plan после разрешения: additive schema, без переписывания существующих well/review/check/alerts; nullable source-backed данные, unknown по умолчанию; source inventory/mapping и quarantine неоднозначных records; dry run counts/hash/provenance, scoped parity; enable одного согласованного сценария. Rollback — disable new writes/read feature, сохранить additive tables/events и экспортируемый recovery snapshot, не drop history. Backfill только из принятого источника с recorded_at загрузки и known historical actor, не генерация прошлой авторизации. Backup+restore/replay проверяется до enable; downstream projection восстанавливается от authoritative facts.

## Excel import: минимальный target contract, WO-X

**Подтверждено требование загрузки и выгрузки; конкретные поля/источник не утверждены.** Первый рекомендуемый import — одна паспортная revision одной существующей разрешённой Pulse well. Начальное ограничение для согласования: существующая equipment identity; отсутствие/неоднозначность связи даёт preview error, а не автоматически созданную установку. Создание equipment, purpose change или assignment — отдельная явно разрешённая команда, если их примет entity/source policy WO-P1. Второй template/slice — одна работа/замена с уже принятыми интервалами, revision и atomic replacement. Большой mixed workbook/много well/batch partial success в первый slice не включать.

Файл — источник заявленных фактов, не доказательство authoritative data. При неизвестном upstream source owner до enable выбирает разрешённую file/manual submission policy и кто подтверждает паспорт/работу. Различать uploader, `source_claim` из файла и проверенную source identity/version, ссылку на документ и verifier/verification status. Server actor commit берётся из текущей session; claimed historical performer/occurred_at/precision — отдельные поля с evidence/unknown. Загрузка сегодня не делает пользователя исполнителем ремонта вчера и не делает historical source подтверждённым. Shared/service identity сохраняется явно, персональный actor не выдумывается.

**Versioned template.** Первый формат — строго XLSX по allowlist, без обещания XLS/XLSM support или round-trip любого report workbook. Лист описания template/schema version, разрешённых sheets/columns/операций и явных единиц/дат; лист данных представляет одну принятую domain command. Предлагаемые технические колонки: template version, Pulse ID, equipment/source namespace+external key при наличии согласованного mapping, operation и expected revisions; поля паспорта добавляются только из принятого domain contract. Server не доверяет embedded version/capabilities: проверяет её против известного шаблона. Старый известный template либо имеет явный compatible parser, либо отклоняется; неизвестные/дублирующиеся headers, sheets/columns и неоднозначное mapping не игнорируются. Template download тоже требует capability/scope и не содержит чужих справочников.

IDs текстовые без преобразования через float/scientific notation: Pulse ID валидируется как точный целочисленный ID, external key с leading zeros сохраняет исходный смысл namespace. Уже потерянная Excel precision не восстанавливается догадкой. Match только explicit Pulse↔external identity; well number и data/app `well.id` не служат fallback. Lookup не раскрывает, существует ли чужая well/equipment; generic inaccessible/unresolved error без закрытых названий. Identity equipment/assignment проверяется в контексте этой well и согласованного интервала. Импорт не создаёт well, не меняет catalogue fund/external mappings, telemetry, risk/check/review/ML output.

Для каждого изменяемого поля предложить явное действие `keep/set/clear` (точное представление в шаблоне OPEN). Пустая ячейка означает no change в patch, никогда скрытое erase; неизвестное значение и clear подтверждённого значения различны. Для первой новой revision обязательные unknown допускаются только по schema policy с quality/reason; mandatory field отсутствие даёт error. `0`/`false` сохраняются. Numeric finite+unit validate до сравнения; nominal/allowed не заполняются actual/setpoint, единицы не конвертируются без принятой формулы. Предпочесть однозначные текстовые даты/время по template contract. Если допускаются Excel serial dates — учесть workbook 1900/1904 epoch, invalid/phantom dates и date-only отдельно от timestamp; timezone/precision явные, неоднозначность или unknown date не подменяются текущим временем. Все эти решения показывает preview.

**Interface и стадии** (предлагаемые пути, не frozen HTTP/DDL):

1. `GET /api/v1/operations/import-templates/{kind}/{version}` — capability+scope до выдачи. `POST /api/v1/wells/{id}/operation-imports` — upload ограниченных bytes и выбор известного template/mapping. До чтения/поиска private targets проверить current import-preview capability и well scope.
2. Bounded XLSX parser возвращает typed candidate command+errors, не пишет domain tables. Server разрешает только approved identity/source/units; создаёт opaque staged import с owner, raw-file SHA, normalized command/fingerprint, template/schema/parser/mapping versions, targets/expected revisions, source claims и expiry. Неизменяемый validated preview содержит sheet/row/field safe errors и diff `create/update/no-change/conflict`, current/expected revision и source/quality/unknown. Formula rejection не маскируется cached value. Ни preview, ни lookup не меняют паспорт/работу. Preview записи — отдельный staging store с частными правами/retention, не принятый бизнес-факт.
3. `GET .../operation-imports/{id}` возвращает preview/status только owner либо специально разрешённому reviewer и после **текущего** scope. Изменение файла, mapping, source choice или исправление ячейки требует нового preview; client JSON diff не подменяет server validated command. Expired/unvalidated/conflict preview не commit-ready. Preview digest не является правом доступа.
4. `POST .../operation-imports/{id}/commit` — явное действие пользователя с request_id и expected preview fingerprint. Current commit capability/scope проверяются до duplicate lookup/receipt; для первого slice рекомендуется тот же uploader account, отдельное delegation approval пока не поддерживать без принятой policy. Сервер берёт command из сохранённого validated preview, сравнивает versions/hash/revisions и source policy, блокирует well/equipment/assignment в стабильном порядке и повторно проверяет interval/ownership rules. Права, выданные при preview, не переигрываются после revoke.
5. Одна bounded domain command атомарно пишет новую passport revision либо work/replacement state, immutable history/source evidence, committed domain event и первоначальный receipt + ссылку committed stage. При любой ошибке всё откатывается; нет частично закрытого A/неоткрытого B, ложного success или скрытой частичной загрузки. Нет silent merge с новой revision после preview: 409 + новый preview с сохранением доступного пользователю draft. State/history/event/receipt должны быть в одной PG transaction; private raw bytes могут храниться отдельно по принятой policy, но их availability/hash проверяются до commit, не dual-write в другой store.
6. `GET .../operation-imports/{id}/receipt` — current auth+target scope прежде чтения. Receipt содержит opaque command/import ID, status, committed entity/revision/history references, file/preview fingerprint и server recorded_at/actor; не full workbook/private cell values. Lost HTTP response после commit безопасно повторяется: тот же namespace key+тот же command fingerprint возвращает **первоначальный** receipt, независимо от последующих revisions; тот же key с другой command/preview →409. Stale expected revision по новому key →409. Committed receipt не запускает parser или новый mutation при повторе. После удаления raw preview по retention должны остаться принятые минимальные command/idempotency/receipt evidence на согласованный срок; сроки OPEN, не брать 7 дней action_log.

Внутри одного command одинаковые/конфликтующие повторные строки запрещены с row errors в первом slice, не суммируются/не выбирается «последняя». Для повторного файла и **нового** request_id content hash — evidence, не глобальный dedup key между сотрудниками. Server связывает preview с уже committed command; попытка повторного commit preview возвращает его receipt после авторизации. Новый preview того же файла должен показать existing revision/no-change либо conflict, не создать duplicate work. Если источник предоставляет устойчивый record key/version, вводится source+record-version dedup с payload conflict; без такого ключа безопасный первый work slice требует explicit target/command identity и не обещает автоматическое распознавание одинаковых исторических ремонтов. Batch позже — отдельный выбор all-or-nothing или независимые команды с явными receipts, без silent partial success.

**Private staging и parser budgets.** Scope/capability до upload/lookup/preview/commit/receipt; file/preview owner из server identity, opaque IDs и no-store для private responses. Raw file/normalized candidate могут содержать персональные сведения: доступ, purpose, retention/TTL, encryption/access policy и cleanup должны быть приняты до загрузки. Sanitized errors не содержат credentials, raw formula/чужих values; O2 logs/traces не получают workbook/cell/filename/actor labels. Crash/cancel/parse failure/expiry cleanup и quota accounting проверяются отдельно; стадия принятого receipt не становится зависимой от живого temp-файла.

Reject formulas во всех разрешённых и лишних sheets/cells, включая cached formula results; macros, external links/relationships, embedded/active payloads и запрещённые workbook parts отклонять. Никакого formula evaluation или сетевых запросов/ресурсов из книги. Проверка контейнера и фактического распакованного потока защищает от ZIP bombs, duplicate/path-traversal entries, ложных sizes/dimensions, чрезмерных shared strings/styles/cells; одних заявленных dimensions или compressed size недостаточно. До parse зафиксировать raw/ZIP entries/actual uncompressed/ratio/row/column/cell/string/processing time/concurrency/RSS/temp budgets, bounded admission и cleanup; неизвестные encrypted/malformed workbook types fail closed. Конкретные числа выбираются и измеряются на репрезентативных разрешённых и adversarial fixtures перед enable; Q0/ML Upload caps не наследуются. Если parser нельзя остановить внутри library call, plan должен предусмотреть изоляцию/worker timeout и bounded resources, а не обещание, что request cancellation немедленно остановит парсинг.

## Защищённая аналитика и навигационный помощник

Предложить capabilities `operations.read/write`, `operations.export`, `operations.import_preview/commit`, `employee_analytics.read`, `help.read` с scope; точные имена/роль grants OPEN. Import preview не даёт commit право, admin role не оправдывает blind overwrite. Текущий admin bypass не доказывает права на новые персональные данные. Для employee analytics требуется personal authenticated identity и отдельное принятое право; legacy/shared не становится сотрудником. Server committed business event — минимальный action ID+target ref+revision+outcome в бизнес-транзакции. Usage client envelope — allowlisted action/route template, server actor/received_at, bounded client timestamp при необходимости, dedup key; это недоверенный attempt/open. Оба потока не O2 logs/traces/metric labels. Никаких field/file/chat contents, keystrokes и off-app tracking; clicks не мера результата работы. Notice, purpose, access, retention/delete и small-cohort disclosure policy должны быть приняты до collection. Публикация aggregates не делает малую группу автоматически анонимной.

Excel: один report snapshot для UI/download и metadata sheet; current auth/capability проверяется при запросе и выдаче. Если async export оправдан измерением — TTL, opaque job ID, owner+current scope, cancel/cleanup и повторная auth download; не public URL. IDs, особенно >2^53, записывать текстом; null/0/false сохранять; unit/source/quality не терять. Для недоверенных strings использовать явный cell string type; тестировать `= + - @` и leading control/whitespace, отсутствие formula records и external links. Не «экранировать» настоящий numeric −1 в строку. Bounded row/bytes/time/concurrency/period budgets и memory/temp proof до enable; текущий encode работает в памяти. Новая библиотека/driver/версия не выбраны.

Help module: server role-filtered knowledge и route catalogue, minimal current page context, doc/source version+citation. Capability check до retrieval и финальных ссылок; и URL/open action повторно проверяет backend. Источник недоверенный: инструкции в документе не повышают права и не становятся tool call. Нет auto writes, оборудования, диагностики/оценки отказа. Curated search/navigation без внешней модели — достаточный исходный вариант. Внешний provider допускается только после принятия egress allowlist, разрешённого контекста, secret handling, per-user/global cost quota, timeout, retention/training/logging и удаления; профиль поставщика/версии пока OPEN. Не помещать закрытые имена в denied ответ/summary/log. Safe fallback — обычная справка/поиск/навигация с сохранением формы при timeout/quota/outage. Мини-робот в каске только brief designer: keyboard/focus/доступное имя, light/dark/contrast, reduced-motion/отключение, не перекрывать аварийный контент; рисунок/Figma не созданы.

## Влияние на будущую Q0 applicability

Это review не меняет Q0 pin/recipe/policy specs и не добавляет поля сейчас. [compatibility](model-rpc-compatibility.md). Изменение metadata не мутирует immutable Q0 input/старый результат, current assignment не подменяет assignment на время входа. Frozen applicability snapshot/versioned decision должен учитываться в agreed request/execution identity, если влияет на результат; нельзя тихо добавить mutable lookup после pin. Required channels/unit/operating regime/quality проверяются отдельно, научная temporal приёмка остаётся deferred. Формат и точный reason code — следующее согласование, не заявленная runtime поддержка.
