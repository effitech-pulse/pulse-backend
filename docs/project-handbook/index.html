Статус · PREP и исполнение O1/F1, 20.10.2026

Изолированный PREP на loopback 8088/8018 проверен с персональным входом и APP_SCOPE=cohort, версия presentation-v1: зафиксированы 100 существующих участников, scope действует на API/экспорт/расчёты без обхода membership администратором. Обычный compose.local также получил local/cohort defaults, но изменение файла не переключает ранее запущенный экземпляр 8080; его рабочие БД и контейнеры в PREP не менялись.

Backend выполняет пользовательский bulk через телеметрию приложения и bundle-only Upload. Полный output snapshot сохраняется неизменяемо; provenance остаётся partial, поскольку точные входные bytes для replay не сохраняются. Senior-замечания PREP закрыты; ограниченный browser gate — 22/22 PASS, без ошибок страницы. Это технические проверки, а не научная приёмка модели. Пользователь отложил внешние данные и подключит ML позже: scientific acceptance not_assessed, продвижения модели нет. SSO, общий предметный журнал, доставка уведомлений, брокер и Kubernetes остаются отдельными задачами; полный перенос Figma не объявлен.

PREP ledger, архитектура, runtime playbook и совместимость семи репозиториев и native artifact hashes фиксируют источники и границы свидетельств. Статус отделяет подтверждённое от оставшихся задач. Push, cloud job и публикация release не выполнялись; горизонт 7–14 суток остаётся целью.

O1/F1 приняты как программное изменение в согласованной области. Core OTel SDK 1.38.0/безопасные JSON logs и шесть вкладок с восемью versioned Figma nodes проверены: task и whole-wave Senior Spec/Standards PASS, findings 0; runtime 12/12 и browser 7+2/9, pageErrors 0, scoped visual PASS. HTTP код обращения отделён от бизнес request_id; exporter/центрального хранилища нет. Execution ledger, O1 contract и runtime playbook фиксируют payload refs, evidence и пределы: нет successful live ML→PG прогона, forced rollover или научной приёмки. Фактические sync/build/validate/ZIP и source check выполняет координатор после этого authored freeze; до них обновление HTML/ZIP не заявлено. PREP manifest сохранён историческим.

Автономный validate.py не требует ни tasks, ни соседних checkout.

Назначение и границы проекта

«Пульс скважины» — система диагностики электроцентробежных насосов нефтяных скважин. Основной пользователь — технолог: он оценивает риск, изучает телеметрию, проверяет модельное подозрение и фиксирует заключение. Администратор управляет реестром, источниками и доступом. Разработчик модели работает в отдельном исследовательском контуре.

Горизонт 7–14 суток — цель проекта. Он не является доказанной характеристикой текущей модели. Подозрение модели не означает подтверждённый отказ; отсутствие достаточных данных не означает нормальный режим.

Основные потоки

  1. Браузер загружает SPA из Nginx. Запросы /api/v1 проксируются к Go API.
  2. Backend разрешает ID Pulse и scope. Читает операционную БД, а при необходимости — историю через Pulse Data.
  3. Сборщик резервирует источник lease, читает пакет JSON/БД, применяет mapping/гигиену и атомарно сохраняет измерения, журнал и watermark.
  4. Ручная проверка читает заданный период телеметрии, формирует CSV, вычисляет SHA256 входа и вызывает gRPC Upload. Результат с идентификатором модели сохраняется в manual_check.
  5. Технолог меняет решение отдельной операцией; версия и предметное событие сохраняются в одной транзакции. Это не пересчитывает риск.
  6. В cohort-профиле прогон фиксирует profile/cohort_version при BeginCohort и использует PostgreSQL advisory lock, затем ReadApp → telemetryCSV → Upload по участникам. Полный output snapshot, тревоги и terminal state записываются атомарно. Отдельный research-профиль сохраняет прежний Score; он не подменяет пользовательский bulk.

Сбор по расписанию не запускает автоматически скоринг каждого пакета. Streaming Upload — передача файла чанками, а не онлайн-обучение и не обработка каждого измерения без окна. Research ML-контекст может строиться лениво по запросу; bundle-only Upload от него отделён; ML_AUTORUN_ENABLED=false отключает ежедневный плановый прогон, но не всякое вычисление по запросу.

Зависимости кода

pulse-data → pulse-model; pulse-ml-service → pulse-model + pulse-contracts; pulse-backend → pulse-contracts. Frontend использует HTTP API; отдельного прямого доступа к БД, ClickHouse или ML у браузера нет. Model не импортирует Data. Повторение имени Python-пакета scripts в model/data учитывается при editable-установках; запускать команды следует из соответствующего репозитория.

Диаграммы C4 выше сохраняют исходную дату и не доказывают переключение runtime. Принятый cohort/provenance seam и уточнения review/browser описаны в PREP architecture; редактируемый draw.io включён отдельно. FundScope объединяет membership и RBAC, typed DecisionRule сохраняет различные политики, PG хранит immutable output. Текущий alert linkage/status добавляется только на чтении как mutable overlay и не входит в output digest. Полный replay не заявляется без неизменяемых входов.

Output и входы PREP

Полный snapshot сохраняет outcomes всех участников, включая non-scored с result=null; reader выдаёт только разрешённое пересечение. Обработка alert/status читается отдельно и не изменяет decision JSON/digest. ml_run.profile/cohort_version фиксируются до операций, которые могут завершиться ошибкой: running/error попытка различима даже без snapshot. Совместимы только пары unknown (NULL,NULL), research (research,NULL) и cohort (cohort,version); существующие строки не получают текущий профиль задним числом.

Immutable output не равен полному воспроизводимому вычислению: точные входные CSV/архивные bytes не сохраняются, поэтому provenance partial. В публичном комплекте только DDL, протоколы и агрегированные технические свидетельства; membership CSV, реальные bindings, dump, телеметрия и секреты не публикуются.

Источники контракта

Полный OpenAPI JSON — копия pulse-backend/api/openapi.json текущего рабочего дерева. ml.proto — копия единственного protobuf-контракта из pulse-contracts. Каталог операций ниже сформирован из OpenAPI; реализацию и серверные права определяют также transport/httpapi/routes.go, access.go и сервисы.

HTTP-префикс по умолчанию /api/v1. Браузер использует тот же origin (PREP http://127.0.0.1:8088, исходный локальный адрес :8080), Nginx проксирует API. В локальном режиме сеанс передаётся cookie pulse_session; в legacy может применяться общий X-API-Key, если ключ задан. Наличие operation в OpenAPI не предоставляет право вызова любой роли.

Идентификаторы и типы

Пользовательские well routes принимают bigint ID Pulse. Не подставляйте в них Unitek/Armits/device ID. Для источника отдельно задаётся well_identity; преобразование выполняется backend. null, отсутствующее поле, false, ноль и пустой массив не взаимозаменяемы. int64 сохраняется в protobuf; входной JSON-адаптер использует числовой тип без раннего float-преобразования. JavaScript-клиент не должен предполагать безопасность произвольного bigint за пределами safe integer; это отдельная граница web-контракта.

Версии и повторные запросы

Для PATCH карточки персональный режим требует revision; при архивировании/восстановлении передаются revision и reason. Legacy DELETE выполняет мягкое архивирование; в local требует If-Match. UI не должен автоматически повторять действие с подставленной новой версией при конфликте: нужно показать актуальное состояние и сохранить пользовательский черновик для осознанного решения.

Ручная проверка использует (well_id,request_id). Повтор того же запроса возвращает сохранённый результат, другой период с тем же ключом конфликтует. Решение технолога также имеет request_id и ожидаемую revision. Это не универсальная гарантия exactly-once для любого API.

O1: HTTP-корреляция

X-Request-ID обозначает конкретную HTTP-попытку, gRPC передаёт его как x-request-id. Допустим один ID из 16–64 ASCII alnum/underscore/hyphen; недопустимый или отсутствующий заменяется случайными 32 hex. Nginx всегда создаёт свой ID и возвращает его также на локальной ошибке; direct Go/Data валидируют независимо. В error UI optional http_request_id берётся только из безопасного response header и отображается отдельным «Код обращения». Тело ответа и DTO ради O1 не расширяются, network-only ошибка не получает выдуманного ID. Стабильный бизнес request_id и fingerprint повторной проверки/review сохраняются при retry. Корреляция не даёт прав и не доказывает provenance. O1/F1 ledger: runtime 12/12 и browser 7+2/9 подтвердили scoped fixtures, whole-wave Senior PASS. Controlled error/409 fixtures не выданы за успешные production writes.

Источники и обработка телеметрии

Настройка источника

Источник имеет имя, kind, status, interval_seconds, endpoint/table_name, records_path, well_field, time_field, well_identity и массив mappings. Секрет передаётся отдельным полем; он не размещается в URL или в открытом config. Сохранение создаёт новую версию профиля; запуск/пауза — отдельное действие.

KindПолучение
json_pullBackend опрашивает разрешённый HTTP(S) endpoint, Bearer token из secret
json_pushВнешний отправитель вызывает ingest работающего источника
postgres / mysql / clickhouseSQL-адаптер читает настроенную таблицу, время и поля
fileРазовый импорт измерений через HTTP приложения

INTEGRATION_ALLOWED_HOSTS содержит конкретные разрешённые hostname. Redirect не выполняется автоматически. Allowlist не заменяет сетевую сегментацию и отдельные read-only credentials БД. Произвольный SQL пользователя не является контрактом формы источника: задаются таблица и поля, строится ограниченный запрос.

Mapping

Каждая строка задаёт field источника, canonical parameter, unit, scale, offset, список missing-маркеров и is_set. Вложенные JSON-пути записываются через точку, например values.F_out. Сначала очищаются маркеры, затем применяется коэффициент/смещение. Уставки не записываются как измерительные каналы.

Пример: настройка JSON-источника, пакет измерений. ID в примере — ID Pulse, не внешний номер оборудования.

Цикл сбора

  1. Планировщик backend проверяет источники; источник должен быть running и наступить next_poll.
  2. ClaimSource атомарно резервирует lease на 60 секунд; конкурирующий сборщик не получает то же действующее резервирование.
  3. Для JSON pull since берётся по last_measured с минутным перекрытием; при отсутствии watermark используется последние 24 часа.
  4. Выполняются fetch, mapping и разрешение ID. Неизвестное/неверное сопоставление не должно молча записывать пакет к другой скважине.
  5. В одной транзакции сохраняются точки и журнал; PK (well_id,measured_at) оставляет дубликаты без перезаписи. Watermark обновляется через GREATEST, error очищается, lease освобождается и рассчитывается следующий запуск.
  6. При ошибке источник получает сообщение и отложенную попытку через 60 секунд. Сам цикл имеет timeout 30 секунд.

Динамические last_received/last_measured читаются из отдельных столбцов, а не из старого JSON-снимка профиля. Для этого есть регрессионный тест: после очередного цикла и повторного сохранения настроек watermark должен оставаться актуальным.

Интервал сбора и интервал обновления браузера независимы. Выбор 5/60/900 секунд в интерфейсе не меняет автоматически частоту датчика или разрешение исходного архива.

Чтение и отображение

Backend объединяет сохранённые измерения и доступный архив по связи скважины. В пользовательском ответе ID снова является ID Pulse. Границы доступной истории запрашиваются отдельно; архивная страница не должна по умолчанию открываться на пустом сегодняшнем дне.

Телеметрия поддерживает совместные каналы, нормированное относительное изменение, две оси, отдельные каналы через настройки, сравнение A/B, общую шкалу и синхронные cursor/zoom. Экспорт сравнения содержит принадлежность к периоду. При нулевой базе относительное изменение не определено, а не бесконечность.

Pulse Data и стандартный источник

Текущий сервис Data использует /health, /v1/fleet, /v1/scenario, /v1/stream, /v1/bounds, /v1/telemetry. В Docker он доступен backend по http://data:8092; loopback внутри backend не указывает на соседний контейнер.

Генератор создаёт 100 обезличенных скважин: 85 стабильных и 15 с постепенными сценариями деградации. Origin, seed, ramp_days и отпечаток профилей фиксируются сценарием. Повторное чтение прошлого детерминировано, будущие точки не выдаются. Truth-разметка сценария не подмешивается в измерения и не назначает модели риск.

Согласованное имя пользовательского подключения — Pulse Connector. Оно не превращает искусственные данные в производственные измерения; сведения о происхождении и NDA остаются в описании источника. Внутренние имена fund_type=presentation, telemetry_emulator и репозиторий pulse-data сейчас ещё сохранены.

Ограничения

Нет автоматического скоринга каждого поступившего пакета и нет брокера. Проверка данных и конфигурации не равна проверке модели. В текущем UI импорт остаётся доступен в интеграциях; его перенос — согласованная доработка. Схемы деградации являются инженерной имитацией и требуют предметной валидации технологом.

Модель и причинная валидация

Текущий исполняемый комплект

Локальный stage1_binary_v1 — исследовательская бинарная CatBoost-модель. Проверка файла строит окна 48 часов с шагом 12 часов; минимальная история — 30 суток. Она возвращает norm/watch/alert/insufficient, timeline, числа доступных/недоступных признаков и объяснение. Это не готовая классификация всех 13 физических причин.

Ручная проверка сохраняет имя, дату и SHA256 комплекта модели, SHA256 CSV-входа, период, число точек и разрешение. Если идентификатор артефакта неизвестен, возвращается null. Не подставляется выдуманная версия.

Contribution содержит value_source: computed, training_median, zero_fallback; у старых результатов источник может быть неизвестен. Заполненный медианой признак не называется измерением датчика. Состав каналов не расширяет автоматически обученный вход модели. features_unavailable должен быть виден пользователю.

Риск и ярус

Риск последнего окна, накопленный ярус и data_ok независимы. Общий typed evaluator применяет явные DecisionRule/policy из согласованного контекста: legacy Score и Upload сохраняют разные шкалы/операторы и K; округлённый display risk не восстанавливает решение. Низкий последний риск или проблема связи не отменяют накопленного яруса. Решение технолога также не меняет его автоматически.

Бинарная модель, калибратор, meta.json и профиль дрейфа передаются согласованным комплектом. Для causal_v1 требуется свой normalizer.pkl. Автоматического выбора latest и продвижения кандидата нет.

Проектная архитектура — маршрутизирующий каскад: гигиена данных → детектор аномалии/дрейфа → маршрутизация по динамике → классификация или survival внутри бакета.

Протокол оценки

Train строго раньше test; группы не пересекаются; purge/embargo удаляют окна у границ. Нормировщик fit только на train, калибратор — calibration, порог — selection. Test используется для отчётности. Контекст соседей и собственной базы строго причинный. SMOTE сырых временных окон запрещён; усложнение принимается только при выигрыше в одинаковом протоколе.

Воспроизведение и продвижение

Из pulse-model: make honest-cache, make honest-eval; эксперимент режима — make regime-cache, make regime-eval. Команды обучают/оценивают модели и требуют подготовленных локальных данных; это не smoke-check веб-приложения.

Перед продвижением: фиксируются данные/код/протокол; проверяются утечки, recall по классам, macro-F1, confusion matrix и заблаговременность; утверждаются пороги и цена ошибок; сохраняется предыдущий комплект. Просмотренный test становится диагностическим и не служит новой независимой приёмкой. Производственная приёмка текущего комплекта ещё не закрыта.

Поддерживаемые RPC и происхождение результата

Матрица моделей/RPC описывает фактическую шкалу, оператор порога, K/lookback, cold start и границы Score/Upload/History. PREP добавил typed decision/provenance и согласованное evidence History; causal Upload явно отклоняется как unsupported_feature_recipe до feature construction, unknown context — как unsupported_context_version. Provenance envelope реализован, но его статус partial: exact input bytes для replay не сохраняются. Поддержка evaluator не является научной приёмкой causal-кандидата. Полный причинный бейзлайн включён как датированный исследовательский источник.

Пользовательский runtime PREP и scientific gate

Upload загружает только bundle модели с thread-safe cache и проверкой fingerprint на запросе и до/после загрузки. Research Score с manifest/cache/PG не является предварительным условием Upload. Cohort backend строит вход через ReadApp/CSV для каждого из 100 зафиксированных участников, сохраняет scored/archived/inactive/insufficient/error и null result у неоценённых; риск 0 не используется вместо отсутствующего результата.

Полный stored output, as_of, bundle/policy identity и digest доступны после restart. Это проверка сохранности результата; immutable input bytes не хранятся и provenance partial. TreeSHAP Upload относится к peak raw-score окну; latest risk/date остаются latest. Computed/training_median/zero_fallback и unknown источник объяснения различаются, включая literal 0.

Независимая приёмка readiness_v1 и публичный пример протокола определяют закрытый test, physical oilfield mapping, availability, обе популяции во всех ролях и раздельные горизонты 7–14/7–30. Валидатор проверен на fixtures; незаполненный пример должен давать blocked. Software PASS не устанавливает истинность меток/независимость данных и не вычисляет научную приёмку: status scientific_acceptance=not_assessed. Пользователь отложил новые внешние данные и подключение ML; новые метрики и продвижение не выполнялись.

Рабочие сценарии и жизненный цикл скважины

Риски и телеметрия

Технолог выбирает скважину по ID Pulse, видит оценку модели и основание яруса, затем изучает телеметрию за соответствующий период. Сравнение периодов должно сохранять реальные временные метки и одинаковый выбранный набор каналов. Недостаток канала/истории показывается явно.

F1 source 20.10 реализует порядок Риски → Телеметрия → Проверки → Отказы → История → Сведения с keys overview, telemetry, checks, failures, history, details. Старый overview, отсутствующий и неизвестный key открывают Риски. Смена вкладки сохраняет run_id, check, остальные query-параметры и hash; push-навигация поддерживает Back/Forward. Паспорт, классификация и осложнения находятся в Сведениях; это текущие сведения, а не паспорт выбранного исторического run. Существующие формы/действия и сохранённый результат используются повторно. Task/whole-wave Senior PASS, browser 7/7 + mobile controls 2/2 и scoped visual/mobile-account PASS закрывают software acceptance. Источники — F1 handoff и execution ledger; controlled409/draft проверен без успешной записи.

Ручная проверка

  1. Выбирается доступная скважина и период не менее 30 суток.
  2. Backend проверяет scope, диапазон и полноту выборки. Truncated не считается полным входом.
  3. Формируется CSV и request_id; модель оценивает окна.
  4. Полный ответ с идентификатором модели сохраняется; пользователь может закрыть вкладку и позже открыть проверку.
  5. Повтор выполняется с тем же request_id только для того же периода. При незавершённой попытке после перезапуска разрешён предусмотренный повтор, но не обещается произвольное возобновление любого процесса в Kubernetes.

Проверка не изменяет текущий ярус фонда. Нельзя заменять сохранённый ответ новым расчётом незаметно для пользователя.

Решение технолога

Оценка модели и обработка случая раздельны. Сервис Reviews валидирует переходы и обязательные данные, получает автора из серверного Principal и атомарно пишет текущую state/revision и review_event. Переданный клиентом произвольный actor не считается подтверждённым автором. В legacy отсутствие персональной идентичности отражается честно.

При конфликте revision возвращается 409; UI показывает актуальное состояние и сохраняет ввод. Закрытие уведомления не подтверждает тревогу. Фиксация физического отказа с датой — отдельное предметное действие, а не переименование любого модельного alert.

Реестр и архив

В отдельно выбранном research-профиле создание не требует внешних Unitek/Armits ID. В cohort-профиле обычное создание/импорт не расширяет неизменяемое membership; новая версия capture не является side effect редактирования карточки. Номер, НГДУ/цех, responsible и active являются отдельными полями. Коды справочников 0 и отрицательные технические коды не теряются. Responsible — подпись ответственного, а не автоматическое назначение прав.

Редактирование использует revision, захваченную при открытии формы. Архивирование/восстановление требуют причины и ожидаемой версии. active при этом не меняется. Истории, проверки, заключения и телеметрия сохраняются; редактирование архивной карточки блокируется до восстановления. Скрытие из оперативного фонда не равно физическому удалению и не прекращает само по себе внешний сбор.

История карточки читается постранично через before; события содержат before/after, автора, время, версию и причину. Просмотр архивной карточки требует include_archived=true и обычного scope. Legacy DELETE сохранён ради совместимости как мягкое архивирование.

Импорт и экспорт реестра

Канонический пользовательский экспорт использует PULSE_ID. Старый четырёхколоночный формат PULSE_ID/WELL_NUMBER/NGDU/CEX сохраняется. Расширение identity=pulse&lifecycle=true добавляет ACTIVE, ARCHIVED_AT, RESPONSIBLE, REVISION. Старый внешний формат не меняется незаметно.

Повторный импорт существующего PULSE_ID пропускает запись и не восстанавливает архивную скважину автоматически. Перед подтверждением показывается предпросмотр. Экспорт и агрегаты должны следовать тем же фильтрам и серверным правам, что список.

Файлы телеметрии

CSV/XLSX/Parquet читаются с выбором колонок, времени, часового пояса и mapping. Предпросмотр показывает отклонённые строки, пропуски и валидные нули. Экспорт включает выбранный интервал/каналы; при сравнении — метку A/B. Формат чтения данных в UI не означает, что gRPC-модель принимает Parquet напрямую: backend приводит вход к контракту проверки.

Сейчас загрузка есть и в интеграциях, и в телеметрии, и отдельной проверке файла. Согласована единая рабочая точка, её перенос ещё не завершён.

Сеансы и пароли

Пароли хранятся как bcrypt cost 12; сеанс использует случайный токен, в БД хранится SHA256 digest. Срок — 8 часов. Cookie HttpOnly/SameSite=Strict, Secure по конфигурации (по умолчанию true). Запросы изменения в local проверяют origin; вход ограничивается по частоте. Смена ревизии/статуса пользователя влияет на его сеансы через серверное хранилище.

Пароль первого администратора передаётся cmd/adminuser только через stdin из защищённого источника. Не включайте пароль в аргументы процесса, команды истории shell, Git или документацию. Полноценные самостоятельная регистрация и восстановление пароля существуют в макетах, но не являются работающим публичным onboarding.

Подключение SSO

Есть auth_identity(provider_id,subject) и сервисная граница внешней идентификации. Полный OIDC login/callback, discovery/JWKS, проверка issuer/audience/state/nonce/PKCE и lifecycle токенов ещё не подключены. Целевой IdP — Keycloak или иной OIDC-провайдер; внешняя identity связывается с локальным пользователем, права/scope определяются сервером. Нельзя доверять роли из произвольного браузерного заголовка.

Секреты и транспорт

Секрет источника шифруется AES-256-GCM. INTEGRATION_SECRET_KEY — 32 случайных байта в base64, хранится отдельно от БД. Копия БД без этого ключа не восстанавливает доступ к источникам; потеря/смена ключа требует контролируемой миграции секретов. Пустой secret не требует ключа.

Сетевой ML transport в текущем локальном запуске использует insecure gRPC внутри Docker-сети; при заданном ML_SERVICE_API_KEY проверяется metadata. Это не mTLS. Для удалённого размещения требуется защищённый транспорт/сегментация и управление секретами. Loopback-публикация текущего Compose не является готовой схемой внешнего доступа.

НДА раскрывается в описании источника; реальные телеметрия, номера/сопоставления и манифест не публикуются с лендингом или документацией. Пользовательское название Pulse Connector не изменяет юридическое происхождение данных.

Свидетельство PREP

Фактический isolated browser/auth gate подтвердил anonymous401, viewer mutation403, forbidden Origin403, logout→401 и повторный вход restricted пользователя без сохранённых admin ссылок/кэша. Scope проверен также на direct ID и Excel; нулевое разрешённое пересечение не превращается в полный фонд. Mobile account/logout и toggle доступны клавиатурой, hidden links исключены из Tab. Это ограниченный runtime gate, не SSO/TLS или полный security/WCAG audit. Даты, отдельные backend/integration и browser результаты — в PREP ledger.

O1: технические logs и spans

В текущем O1 source Go API и Python ML/Data используют core OpenTelemetry API/trace SDK 1.38.0 и allowlist JSON logging. Общие поля: timestamp, severity_text, event_name, service.name, service.version, service.instance.id, deployment.environment.name; при активном контексте — http_request_id, trace_id, span_id. Optional typed duration/status и static error_code не содержат сырые error/stack/payload. Record≤8192 UTF-8 bytes; секреты, metadata, SQL params, query/path IDs, filename/telemetry/comment и персональные данные не сериализуются. Неизвестные diagnostics получают фиксированный fallback event.

Spans охватывают реальные HTTP/gRPC/PG-вызовы; Upload заканчивается с terminal result/error, без span на chunk. PG-only check не получает фиктивный Data leg. Background operation связан с инициатором и сохраняет прежний lifecycle. Runtime provider имеет sampler 100%/bounded span limits, без сетевого exporter, очереди или retention list; test exporter используется только в тестах. O1 не предоставляет центральный поиск и не создаёт предметный журнал/уведомления. O1 contract и execution ledger фиксируют software acceptance: root runtime 12/12 подтвердил actual Go→ML invalid-CSV Upload 422/no-persist и Go→Data unsaved connection check 503/no-import с общими trace/attempt IDs, whole-wave Senior PASS. Полный assembled parent-ID graph и успешный ingest/scoring→persist этим smoke не заявлены; точные parent/link relations подтверждены отдельными SDK/exporter/listener tests.

Надёжность и доставка

Рекомендуемый способ — transactional outbox в той же транзакции, что предметное изменение. Отдельный dispatcher публикует/обрабатывает события; потребитель устраняет повторы по event_id. Повтор доставки не должен создавать второе заключение или второй факт отказа. В текущем коде общего outbox/dispatcher ещё нет.

По умолчанию пользователь выбрал новые тревоги и ошибки сбора. Ошибки глобальных источников не раскрываются роли, которая не имеет к ним доступа. Короткие сообщения автоматически скрываются через 4 секунды, максимум три одновременно; закрытие сообщения не меняет обработку случая. Прочитано, отправлено в SMTP, принято SMTP и доставлено адресату — разные состояния.

Для почты ещё требуются группы, scope, расписание/cron, шаблоны, подтверждение тестовой отправки, очередь и журнал попыток. До настройки адресатов/SMTP письма не отправляются. Предлагаемая очередь RabbitMQ или Kafka не является уже работающей подсистемой.

Два вида проверки

Автономная проверка не требует workspace, сети, модели или БД. Из распакованного handbook:

sh
python3 tools/validate.py

Она проверяет локальные ссылки/HTML-якоря, OpenAPI refs, draw.io, контрольные суммы, SHA256 локальных snapshots и состав ZIP. Ссылка на файл вне package root недопустима. По автономному PASS нельзя заключать, что исходники не изменились после создания снимка.

Сверка с исходниками выполняется отдельно при наличии семи checkout. Передать корень repository-split явно:

sh
python3 tools/sync_sources.py --workspace /path/to/repository-split --check

Она сравнивает источники, локализованные копии и inventory, выявляя изменённые, новые и удалённые публичные исходники. --check ничего не записывает; отсутствие checkout или несовпадение — ошибка, не допустимый SKIP публикационного gate. Готовый ZIP остаётся автономным и не запускает эту проверку автоматически.

Регрессионные проверки инструмента с временными fixture-копиями выполняются из полного workspace:

sh
python3 tools/test_sync_sources.py -v

Они проверяют source/new-file/snapshot drift, восстановление sync, отсутствующие/устаревшие checksums, различие bytes/file-set ZIP, path traversal и автономный validate распакованного пакета после удаления fixture workspace. Исходные репозитории, Git index, данные и runtime этими тестами не меняются. Git-метаданные временного fixture подставляются отдельно; чтение реального Git при финальном sync проверяется публикационным проходом.

Публикационный проход

  1. Принять изменения соответствующих модулей, зафиксировать результаты в журнале и закрыть review. Tech-lead сверяет основные главы с фактами, включая текущие профили запуска и явно обозначенные цели. Не менять продуктовую реализацию ради синхронизации документации.
  2. Выполнить python3 tools/sync_sources.py --workspace /path/to/repository-split --sync. Команда обновляет только mapped snapshots, source inventory/метаданные и таблицу версий главы 18. Основные главы и статусы вручную оцениваются отдельно; sync не выводит их из кода.
  3. Выполнить python3 tools/build.py, python3 tools/validate.py, затем внешнюю --check. Проверить поиск/навигацию HTML и перенесённые темы/диаграммы по изменённой области. Новые результаты занести в журнал; после записи журнала повторить sync/build/validate/check, чтобы source inventory учитывал финальное содержимое журнала.
  4. При передаче архива дополнительно проверить validate.py в отдельной копии без соседних репозиториев. Этот проход создаёт файлы документации, но не публикует release/PR/сайт.

Исключения и отсутствие цикла хешей

Публикационный снимок соответствует public working tree, а не только HEAD/индексу Git. Inventory автоматически учитывает допустимые публичные untracked документы, включая отдельные assistant/concept предложения других владельцев; их наличие/hash не означает принятую реализацию, принадлежность автору публикации или включение в его commit. Mapped snapshots назначаются реестром отдельно с владельцем; SDD/private runtime evidence в комплект не копируются. В итоговом отчёте различаются authored changes, generated snapshots/inventory и чужие public inputs. Внешний --check подтверждает соответствие этой базе, не чистоту Git или remote publication.

Source inventory содержит публичные текстовые исходники/конфигурации разрешённых расширений и Makefile/Dockerfile. Каталоги данных, окружений, Git, node_modules, build outputs, кэши, исторический archive/reference, секреты .env*/ключи/credentials и symlinks исключены. В индекс не входят бинарные веса, реальные выгрузки и сам project-handbook. Отдельные публичные SVG/PNG входят только в явно назначенные snapshots реестра, а не в общий текстовый source inventory. Наличие секретного/data-пути в реестре отклоняется. Полный preflight источников и targets проверяет каждый компонент на symlink и повторно проверяет resolved области до чтения mapped source или записи копий; некорректный реестр не создаёт частичных результатов. Политика индексации также пропускает приватные каталоги .aws/.ssh и не следует symlinks. Временные SDD-заметки в .superpowers/ исключены из обхода и запрещены как explicit registry source/target; долговечные requirements/evidence живут в модульных docs. Это исключение не скрывает произвольные dot-каталоги.

Исключение самого handbook из source inventory устраняет самоссылку. Локальные checksums охватывают комплект, кроме checksums и ZIP; ZIP содержит подготовленные файлы и checksums, но не самого себя. Изменения опубликованных копий всегда выполняются через источник/реестр, а не ручной правкой generated копии. Для нового вида документа/расширения сначала определить безопасное правило включения и владельца.

Архивные task-источники

В реестре source_kind: archived_task обозначает шесть опубликованных исторических документов с originals в необязательном tasks/pulse-backend/docs/ вне checkout. Остальные103 записи имеют обязательный вид repository по умолчанию. Архив задач не включается в публичный source inventory.

Доступный original проходит обычные check/sync и обновление обеих SHA. При его отсутствии check/sync сохраняют bytes снимка и обе SHA: обязательны существующий snapshot, валидные source/snapshot SHA256 metadata и совпадение фактической SHA снимка. Неполный или повреждённый fallback блокирует весь sync до записи. Это подтверждает целостность сохранённого снимка, но не соответствие недоступному original. Изменение snapshot_date не перерисовывает retained snapshot.

Обновление: скорректировать ссылки доступных originals, выполнить sync, затем build и validate. Полный workspace source-check требует семь checkout, но допускает отсутствие только архивных originals; автономный validate проверяет поставленный пакет без workspace и tasks.

Правило приёмки и публикации

В результате проверки записывают ID задачи, базу/состав diff, runtime, команду, дату, exit code и counts passed/failed/skipped с причинами. Для внешнего CI сохраняют ссылку на конкретный job; если он не запускался, так и указывают. JUnit, локальный лог или подписанный результат сопровождают проверяемый diff, а не только имя ветки. Ветку с незакоммиченными изменениями нельзя восстановить одним HEAD.

Обязательная проверка с ошибкой или пропущенной зависимостью остаётся открытой. Допустимый SKIP относится к конкретному опциональному сценарию и не расширяется на весь gate. Нельзя подменять отсутствие результатов зелёной общей надписью. Перед изменением protobuf/SDK/миграций нужны соответствующие контрактные и integration проверки; очередь A таких изменений не выполняет.

Обновление этой матрицы требуется при изменении Makefile, package scripts, CI, runtime profile или условия SKIP. DOC-07 связывает её с README и автономным handbook. Термины и источники

context_version определяет признаки, policy_id — правило решения, model_version — fingerprint bundle. Они не заменяют друг друга. Bundle-only Upload и пользовательский фонд

PREP отделил Upload bundle от research get_context/Score. Thread-safe cache читает только артефакты модели; fingerprint проверяется на каждом запросе и до/после загрузки. Смена bundle вызывает reload, изменение во время чтения отклоняется. Health bundle не загружает. Research Score/History по-прежнему зависят от cache/manifest/справочников и своего ленивого context; Upload без этих входов проверен отдельно.

Upload строит48-часовые окна с шагом12часов из файла. Недоступные features получают training medians drift_profile, иначе zero fallback; прочие NaN —0. Contribution.value_source раскрывает computed/training_median/zero_fallback. Cold start/недостаток признаков не является наблюдением «норма». Отмена RPC не гарантирует остановку уже выполняющегося pandas/CatBoost.

В APP_SCOPE=cohort backend использует ReadApp→telemetryCSV→Upload и сохраняет100 outcomes зарегистрированного cohort. Membership независимо от active/archive/ML-eligible; non-scored result/risk=null и явная причина. Research Score не вызывается вместо пользовательского bulk. Показательный синтетический источник не является независимым ML holdout. Технологический review — изменяемый read-side overlay, не изменение immutable decision facts; источник peak/latest SHAP и value_source сохраняются.

Реализованный wire и provenance

Typed optional additivity в contracts: SnapshotResponse provenance/decision_rule; WellRisk decision; HistoryResponse provenance/decision_rule/accumulated counts; RiskPoint и TimelinePoint raw_score/watch_fired/high_fired; UploadResponse provenance/decision_rule плюс прежние identity16–18. ThresholdRule содержит scale/comparison/threshold/K/optional lookback; DecisionRule — context_version/policy_id/rule_sha256/watch/optional high/high_enabled. Номера/package/старые requests не менялись, SDK официально сгенерированы. Contracts metadata0.1.1 не означает опубликованный новый tag; PREP source commit 07213c430318affd140f55dea391cdc36220d93f.

Envelope содержит snapshot_id/computed_at, bundle identity, context version, recipe/schema/runtime/source hashes и typed manifests, input_kind/context_completeness/provenance_status. Upload input digest вычисляется по точным CSV/XLSX bytes; model identity — по тому же загруженному bundle (meta/model/calibrator/normalizer/drift_profile с учётом отсутствующих файлов). Snapshot/History делят provenance текущего in-memory context.

Статус provenance всегда partial. У research нет immutable input cache/manifest/PG, единого event-time cutoff и достоверного input_snapshot_id/as_of: отсутствующие поля не выдумываются. Source manifest описывает доступные файлы установки, а не immutable загруженный код. Bundle/source/runtime/input hashes без сохранённых входных bytes и доступного runtime не гарантируют повторный расчёт. Public envelope не включает реальные well ID, локальные абсолютные пути, DSN, credentials; digest не заменяет управление доступом к закрытым manifests.

Backend сохраняет полный output snapshot в PG JSONB атомарно с алертами/finish. Чтение выбранного run после refresh/ML restart возвращает сохранённый ответ без нового ML. Это проверка неизменности выхода, не replay входа. Ошибка/рестарт не публикует неполный snapshot как done; версия11 фиксирует profile/cohort_version при BeginCohort до потенциальной ошибки Members. Повторная запись не создаёт вторую несовместимую идентичность.

Новый consumer со старым server читает отсутствие envelope как unknown. Старые consumers читают прежние поля нового сервера. Исторические runs/manual checks остаются доступными без retrofill текущими model/as_of/cohort. Pre11 attempt profile остаётся NULL; отсутствие identity не выводится из started_at/model_name.

Что остаётся целевым

Полный воспроизводимый пересчёт требует immutable входных bytes/справочников/availability cutoff, точного bundle/runtime, retention и измеренного tolerance raw/risk на заявленной platform. Tier/пороговое решение не должны расходиться даже в пределах tolerance. PREP не сохраняет immutable input archive и не утверждает complete replay. Брокер/новый сервис не требуются для реализованного partial provenance.

Научная приёмка отложена пользователем до новых данных: physical oilfield mapping, непрерывное наблюдение нормального/отказного фонда, закрытый test и согласованная стоимость ошибок. Метрики7–14/7–30суток и industrial quality не выводятся из software tests. DOC-04 и PREP не продвигают causal или отклонённый regime-кандидат.

Q0: строгая проверка сохранённого synthetic input

UploadPinned — отдельный streaming RPC SDK0.1.2; первый chunk содержит только PinnedUploadHeader{pin,input}, остальные — только canonical content (≤1 MiB/chunk, ≤50 MiB total). Старый Upload сохраняет прежнее поведение. Сервер проверяет API key, mandatory identity, exact canonical SHA/length и перед features сравнивает actual bundle, decision rule, schema, recipe, source/resources и runtime с полным pin. Несовпадение/утрата bundle даёт FAILED_PRECONDITION; invalid header/hash/CSV — INVALID_ARGUMENT; пределы/result cap — RESOURCE_EXHAUSTED. Downgrade на Upload нет.

ML_BUNDLE_REGISTRY указывает на отдельный operator-owned registry, отличный от mutable ML_DATA_ROOT/models. Ни browser, ни RPC не импортируют pickle. Доверенный оператор может использовать python -m pulse_ml.bundle_registry import --source <trusted-local-bundle> --registry <separate-root>: importer проверяет basename/file inventory, копирует файлы без symlinks/hardlinks, fsync и atomic no-replace публикует <registry>/<64hex>/. Существующий digest не заменяется; GC не выполняется. Hash удостоверяет целостность, а доверие к executable pickle остаётся обязанностью оператора. На каждой попытке, включая warm cache (max1, отдельно от legacy), все файлы/optional absence проверяются заново; loader читает private verified snapshot.

Trusted local helper describe_execution_pin(name, digest, registry_root=Path(...)) в pulse_ml.pinned_upload возвращает JSON-compatible typed pin из actual loaded policy/schema/config/source/runtime без вычисления features/predict и без путей. Код/установленные зависимости должны быть read-only, без hot reload; после смены wheel/runtime нужно получить новый pin. Это helper, публичного describe RPC нет. Strict CSV принимает header timestamp + sorted known canonical measurements/debit, UTC RFC3339Nano с Z, sorted unique timestamps, finite numeric или empty missing; не выполняет alias guessing/resample/source reads. Bounds: 100000 rows,64 targets, 64KiB field,30–366days; результат≤2MiB с явным отказом без truncation. Hygiene до агрегации сохраняет marker/valid zero semantics, raw >/K и norm/insufficient.

Работа исполнителя

  • Один процесс владеет моделью и кэшем. Несколько реплик потребуют общего хранилища результатов.
  • Пересчёт сериализован. Успешный контекст публикуется атомарно; ошибка оставляет предыдущий. Чтение готового контекста работает во время пересчёта.
  • После рестарта research context и отдельный Upload bundle загружаются лениво; Upload не вызывает Score/get_context и не требует research cache/manifest/PG. Bundle fingerprint проверяется на каждом запросе и до/после загрузки. Health не загружает модель.
  • Отмена RPC проверяется до/после вычисления и между чанками; уже выполняющийся pandas/CatBoost вызов автоматически не прерывается.
  • SIGTERM/SIGINT даёт активным RPC до 300 секунд на завершение.
  • Транспорт по умолчанию без TLS: loopback или защищённая внутренняя сеть.

O1: локальная наблюдаемость транспорта

gRPC executable пишет в stdout ограниченные JSON records (не более 8192 байт): UTC timestamp, severity/event, service identity и безопасные status/duration. x-request-id — ID попытки, отдельно от бизнес request_id: одно значение [A-Za-z0-9_-]{16,64}, иначе новый случайный 32-символьный hex. W3C traceparent валидируется официальным propagator (одно видимое значение, до 512 байт); baggage/tracestate и ключ x-ml-api-key не попадают в события/spans. В grpcio 1.78 C-core нормализует повторные wire traceparent до последнего значения ещё перед Python interceptor: этот слой проверяет доступное ему значение, а распознавание исходных wire-дублей не обещается. ID/parent не влияют на auth.

Core OTel API/SDK 1.38.0, semconv 0.59b0: manual SERVER span охватывает выполнение unary и весь stream-unary Upload, включая чтение чанков, создание результата, отказ авторизации, ошибку и отмену. Контекст очищается в finally. Отмена по-прежнему не гарантирует прерывания pandas/CatBoost. В production provider с локальным 100% sampler нет exporter, сети, retention списка или batch queue; exporter используется только в тестах. Resource строится явным allowlist, OTEL_RESOURCE_ATTRIBUTES не импортируется. SERVICE_VERSION (по умолчанию unknown) и DEPLOYMENT_ENVIRONMENT (local) допускают до 128 безопасных ASCII символов; instance — случайный opaque ID. Span limits: attributes 32, events 16, links 8, string attribute 256. Debug выключен по умолчанию.

Только фиксированные события и разрешённые поля проходят форматтер: без bodies, имён файлов, телеметрии, metadata maps, raw exception/message/stack и credentials. Неисправный formatter/stdout sink не меняет ответ RPC; потеря диагностики возможна. Stdout сам не гарантирует retention или отсутствие OS blocking. Runtime profile координатора должен задавать Docker local, max-size=10m, max-file=3; CLI retention задаёт launcher. Collector и централизованное хранение относятся к O2.

Проверка: python -m pytest tests/test_observability.py; реальные listener-тесты требуют разрешённого loopback. API/SDK требуют Python >=3.9 и не повышают declared floor проекта >=3.11. Сохранённый численный runtime-profile с numpy 2.5.1 требует Python >=3.12; нативный O1 smoke выполнен на Python 3.13. grpcio 1.78.0/protobuf 6.33.6 и численные constraints сохранены. Это software gate, не оценка качества модели.

Исправления расчёта признаков

  • Собственная база: только первые 30 окон, завершившиеся до момента прогноза. Первое окно имеет неизвестную базу, а не искусственный ноль.
  • Соседи: последнее доступное значение каждой скважины на момент t, не среднее по всей будущей неделе. Одна скважина имеет один голос; данные старше 7 суток исключаются.
  • Нормировка: медианы и IQR обучаются только на train. Для неизвестного НГДУ используется общий train-масштаб; статистики test не подмешиваются.
  • Контекст без нормировки пересобран из features_v3. Старые запечённые field_z не допускаются новым оценочным скриптом.
  • Контракт causal_v1 сохраняет нормировщик в normalizer.pkl. Для прежних весов сервис явно воспроизводит legacy_v0, чтобы не подменять входные признаки после обновления кода.

Причинный датасет содержит 168242 окна и 975 скважин после исключения окон ближе 7 суток к отказу и отрицательных примеров без полного 30-дневного наблюдения. Пересчёт оптимизирован: 3,52 секунды вместо первоначальных примерно 81 секунды; совпадение со всем сохранённым датасетом проверено.

Независимая оценка

Четыре части разделены по времени и группам: обучение → калибровка → подбор порога → финальный test. Границы заранее фиксированы: 1 января, 1 марта и 1 мая 2026 года. Purge — горизонт 30 суток плюс окно признаков 2 суток; embargo — 3 суток. Нормировщик фитится только на train, isotonic — только на calibration, порог — только на selection. Test участвует исключительно в отчётности.

Тестовые группы пяти разбиений не повторяются и вместе охватывают все девять НГДУ. Полный справочник физических месторождений отсутствует: использована имеющаяся группировка НГДУ, и её нельзя выдавать за проверенный физический справочник месторождений. Внутри каждого разбиения НГДУ и скважины разных частей не пересекаются.

Бейзлайн — CatBoost 400 итераций, depth=6, learning_rate=0.05, те же веса классов. Решение о тревоге: сырой P > threshold и минимум K окон за последние 14 суток. Одинаковое правило применяется при оценке и для causal-комплекта в сервисе. Калиброванная вероятность используется для отображения, не для приблизительного переноса строгого сырого порога через ступеньки isotonic.

На 34 отказах и девяти административных группах результат — диагностический бейзлайн, не окончательная промышленная оценка.

каналов, отдельная доля совместного роста.

legacy сохраняет общий API-key/локальный сеанс с административными правами. local включает персональные сеансы и роли; сначала оператор явно применяет миграции и создаёт первого администратора через bin/adminuser с паролем из защищённого stdin, затем меняет профиль и перезапускает API. Backup/migration/bootstrap/capture обязательны до запуска; порядок PREP.

HTTP API_KEY, внутренний ML_SERVICE_API_KEY, ключ шифрования интеграций и пароли БД — разные секреты. Наличие одного не включает другой. Plain-text gRPC ограничивается loopback/защищённой внутренней сетью. Как согласованно задать внутренний ключ и проверить probe без его вывода: эксплуатация.

Некорректные числа, boolean, timezone и JSON, перечисленные в Config.Load, отвергаются при старте; адреса интеграций/ключ AES проверяются при использовании. CORS не является аутентификацией. Секреты, пароли и живые .env в Git и журналы не включаются.

Задания и остановка

Ручной запуск: POST /api/v1/ml/wells/refresh. Повторный запуск во время действующего lock возвращает 409. История: GET /api/v1/ml/runs. Совместимый PATCH статуса тревоги принимает new, acknowledged, false_positive.

Предметная обработка через review — отдельная модель: status=new|in_progress|closed, а при closed обязателен conclusion=confirmed|not_confirmed|inconclusive и комментарий. Для in_progress/closed нужен ответственный, для изменения — ключ запроса и revision. Review записывает историю и отображает состояние обратно в совместимое поле тревоги: new → new, in_progress → acknowledged, closed/not_confirmed → false_positive, closed/confirmed → confirmed, closed/inconclusive → inconclusive. Поэтому чтение статуса может вернуть пять значений; расширять старый PATCH до пяти нельзя. Статус обработки, заключение технолога и вычисленный ML-ярус — разные поля. Источники: reviews.go (исходник pulse-backend/internal/service/reviews.go; в пакет не включён), руководство (исходник pulse-backend/docs/telemetry-integrations.md; в пакет не включён).

SIGINT/SIGTERM прекращает приём запросов и дожидается принятых прогонов. После аварии PostgreSQL освобождает lock; следующий прогон помечает незавершённые записи как error.

Timeout gRPC не прерывает уже выполняющуюся функцию pandas/CatBoost автоматически. Score не повторяется backend автоматически. Исполнитель ML пока один, с кэшем в памяти; долговечной очереди заданий нет.

Проверка ML и внутренний ключ

Профили HTTP и gRPC независимы. AUTH_MODE=legacy остаётся code default; текущие Compose задают local и cohort. До запуска нужны явные миграции/capture/bootstrap первого администратора, с точными CORS origins и подходящей Secure cookie. См. все настройки и defaults и порядок персонального входа (исходник pulse-backend/docs/telemetry-integrations.md; в пакет не включён). Исходный работающий pulse-local8080 не переключался в PREP; file defaults и фактически запущенный экземпляр различаются.

В ML пустой/отсутствующий ML_SERVICE_API_KEY отключает проверку metadata. Непустой ключ требует точного x-ml-api-key во всех RPC, включая Health. Если оператор включает ключ, он должен явно задать одно значение в backend и в окружении ML-процесса; Docker probe наследует окружение ML. Обычный compose.local сам не добавляет ключ и не переносит переменные host shell в контейнер: используйте согласованный deployment override/средство доставки секретов для обоих сервисов и перезапустите их. Проверку выполняйте без echo, shell tracing и вывода разрешённой Compose-конфигурации с секретами. HTTP API_KEY/X-API-Key этим ключом не являются.

Из установленного окружения ML или внутри его контейнера:

sh
python -m pulse_ml.healthcheck
# Для другого согласованного loopback-порта:
python -m pulse_ml.healthcheck --target 127.0.0.1:50052

Probe обращается к 127.0.0.1:50051, timeout 3 с, проверяет status=ok, закрывает канал и возвращает 0 только при успехе. При непустом ключе читает его из env процесса, не из .env и не из argv. При auth/transport/deadline/неверном status код ненулевой; вывод содержит только безопасную категорию ошибки, без ключа/деталей RPC. Ключ для metadata должен состоять из printable ASCII (0x20–0x7e); Unicode/управляющие символы отклоняются без traceback, допустимые пробелы не обрезаются. Docker/compose.local используют interval15с; isolated compose.prep —10с. Timeout5с и start_period30с; default probe RPC timeout3с. 0.0.0.0 — bind сервера, не адрес клиента. Если сервер слушает другой адрес/порт, endpoint probe меняется согласованно. Health подтверждает listener/доступ, но не загрузку модели, наличие cache/manifest/PG или качество Score. Автопрогон в локальном Compose остаётся выключенным. Plain-text ML listener не публикуется наружу; используйте loopback/защищённую внутреннюю сеть.

Сквозная проверка

make check, make build и TEST_DATABASE_URL=... make integration выполняются из pulse-backend. Integration использует отдельную PostgreSQL и временные схемы, а не рабочую esp_app. Тесты RPC/nullable/int64/экспорта и fixture ML не подтверждают научное качество.

Прогоны, происхождение и исторические записи PREP

В cohort пользовательский refresh читает app-телеметрию и вызывает bundle-only Upload для каждого подходящего участника. Все100 outcomes сохраняются атомарно с завершением/алертами: scored содержит result; archived/inactive/insufficient/error — null result и причину. Это синтетический presentation фонд, не ML holdout. Research Score доступен только отдельному профилю.

С версии11 попытка получает profile/cohort_version на BeginCohort до чтения members; ранний failed/running run не исчезает из истории. Внешний failure reason обезличен. Legacy pre11 записи остаются unknown; текущий cohort им задним числом не присваивается. Статус технолога — изменяемый read-side overlay; immutable decision snapshot/digest при его изменении не переписывается.

Сохранённый snapshot читается после ML restart без нового вычисления. Typed provenance имеет статус partial: bundle/runtime/source/policy/output identity и hash входа не заменяют сохранённые immutable входные bytes. Нельзя обещать полный replay/as-of или промышленное качество. Источники решения SHAP/окна и computed/training_median/zero_fallback не скрываются.
