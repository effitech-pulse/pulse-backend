# Pulse: наблюдаемость и долговечные задания — предложение 20.10.2026

Статус: **план на согласование, не разрешение реализации/развёртывания**. Владелец архитектуры — architect-analyst, общего [плана работ](functional-roadmap-2026-10-20.md) — tech-lead. PREP/DOC приняты, не запускаются повторно. Здесь не меняются source/configs/БД/контейнеры/Figma и не выбирается новая модель. ML/внешние научные данные отложены пользователем (`not_assessed`); остальные integration-функции этим не отложены.

**Рекомендация:** O1 — единые JSON-логи и correlation/context параллельно F1 карточке; O2 — один bounded OTel stack и сквозной trace реального check; Q1 — один RabbitMQ + Go worker для **file-check**, только после immutable input/bundle contract; Q2 — затем durable bulk с fencing/checkpoints. Предметный журнал F3 остаётся отдельной read-моделью committed facts, F4 read-state не требует брокера. Нельзя делать F1 зависимым от всего infrastructure проекта или незаметно менять старый HTTP200 на202.

## 1. Текущий runtime: что проверено по исходникам

## 2. O1: общий contract логов и корреляции

**Один JSON record на событие**, timestamp UTC, severity, event_name, service.name/version/instance.id, deployment.environment, message, safe error.type/code, duration/status; при наличии trace_id/span_id и `http_request_id`. Go — slog JSON handler; Python — logging formatter/adapter; Nginx — JSON access log, error stream отдельно от access и с ограниченной нормализацией. stdout сохраняется независимо от backend наблюдаемости. Debug выключен по умолчанию; stacktrace — ограниченный структурированный field после redaction, не multiline неограниченный repr.

`http_request_id` — opaque ID конкретного HTTP attempt, выдаётся в header/безопасной ошибке. Существующий business `request_id`/idempotency key имеет другой смысл: он стабилен при retry операции, не переименовывается и не заменяется trace ID. В логах использовать отдельное operation reference/digest, не raw неконтролируемый ключ. job_id/run_id/check_id — ссылки на бизнес-факт, не идентификаторы trace. Trace не является авторизацией или provenance доказательством.

HTTP/Gin→outgoing HTTP Data→gRPC client→Python server передают W3C traceparent; SDK/interceptor создают spans, logging context берёт trace/span из active context. Gin route template вместо URL с конкретным ID/query. Nginx передаёт context/локальный correlation ID; начальный server trace допустимо начинать в API без Nginx instrumentation module. Trace headers приходят из недоверенной стороны: валидировать формат/размер, не принимать роль/scope/sample policy из них; baggage/tracestate по умолчанию не переносить без allowlist. Контекст не должен переносить cookies/API-key. Модель распространения и связь логов с trace — по [OTel propagation](https://opentelemetry.io/docs/concepts/context-propagation/) и [OTel Logs model](https://opentelemetry.io/docs/specs/otel/logs/).

Первый сквозной сценарий — **существующий** period check: HTTP request→scope→PG telemetry→canonical CSV→ML Upload RPC→result persist. `ReadApp` дополнительно вызывает Read/Archive HTTP **только** при ненулевом Unitek binding и непустом archive BaseURL; для PG-only скважины Data child span не выдумывается. Data coverage проверяется на явно настроенной mapped fixture либо отдельной реальной цепочке collection Go→Data HTTP→PG с operation/trace link. Новый file-check не является prerequisite. Логировать стадии/длительность/счётчики, не значения каналов. Goroutine bulk/collector получают явный context/correlation: detached background work не должен держать HTTP cancellation, но сохраняет link к инициатору; плановый цикл имеет собственный operation/trace.

**Privacy:** allowlist attributes до export. Не писать password/cookie/token/Authorization/x-ml-api-key/DSN credentials, file content/bytes, telemetry values, исходный filename/path, raw query strings/SQL params, реальные external well IDs/номера, свободные review comments/uncensored exception. SQL spans — operation/table/template без bind values; gRPC — method/status/size bucket без payload/chunks. Допустимые opaque refs с operational access; public error — безопасный code+http_request_id. Collector redaction — второй барьер, не замена source sanitization. Не исправлять query secrets regex только после их сохранения. [OTel sensitive data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/).

O1 fail-soft: exporter disabled/unavailable не мешает login/check/persist; stdout и bounded local rotation остаются. Validate malformed correlation/log injection/oversized attributes. Нет public endpoint выгрузки private logs; frontend показывает request ID в текущем error UI. Технические logs/spans не заменяют action_log/review_event/журнал бизнес-фактов.

## 3. O2: предлагаемый минимальный complete stack

**Рекомендуемый полный пилот:** один OTel Collector-contrib → Loki(logs), Tempo(traces), Prometheus(metrics) → Grafana(общий UI). Пять инфраструктурных процессов в отдельном optional local profile/ops network с volume budgets и закрытыми endpoints. Это не новая бизнес-микросервисная декомпозиция. Tempo не ставить одновременно с Jaeger без отдельной причины; минимальная альтернативная trace-проба — Collector+Jaeger UI и пока local JSON logs, но она не закрывает централизованный log search. Managed backend допустим только отдельным решением о размещении закрытых данных. [Grafana OTel architecture](https://grafana.com/docs/opentelemetry/), [Tempo](https://grafana.com/docs/tempo/latest/).

**Конкретный portable ingest для нынешнего Docker Desktop:** Go/Python logging bridges экспортируют тот же sanitized event по OTLP в Collector; stdout остаётся локальным fallback, **его повторно не tail-ить в тот же central pipeline**. SDK/bridge версии и log API maturity проверяются clean-install тестом на Go1.25/Python3.13 и существующих grpc/protobuf/native pins до implementation; неизвестная совместимость не объявляется готовой. Browser напрямую к Collector не подключается.

Nginx JSON access logs пишутся в явно выделенный shared named volume с bounded rotation; Collector `filelog` имеет только read-only этот volume и checkpoint storage, не host Docker root и не `/var/run/docker.sock`. Ошибки Nginx имеют отдельную bounded parsing/allowlist policy; unparseable/private record не публикуется как raw. Rotation и доступность чтения реально проверяются на Docker Desktop; локальный stdout может иметь отдельный формат, но central record должен быть один. `filelog` — компонент contrib, текущая docs помечает logs beta: pin/test этого receiver обязателен, не «стандартный Collector всё умеет». [Filelog primary source](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/filelogreceiver). Альтернатива отдельного транспорта — Nginx syslog→Collector syslog receiver; это иной проверяемый adapter, не обещание lossless UDP. [Nginx syslog](https://nginx.org/en/docs/syslog.html), [Collector syslog receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/syslogreceiver).

**Bounds:** SDK queue/batch/export timeout, Collector memory limiter/batch/bounded exporter queues/retry deadline; optional file_storage WAL с отдельным ограниченным volume. Backpressure наблюдаемости не становится backpressure бизнес-API. Overflow/disk-full/retry exhaustion дают drops+health/metrics, не нулевую потерю и не бесконечную память. Collector/WAL не источник истины задания. [Collector resiliency](https://opentelemetry.io/docs/collector/resiliency/).

Предложение для pilot, не согласованный SLA: в локальном контролируемом pilot —100% traces при hard budgets/rate limits; это не production baseline. После измерения steady traffic можно отдельно согласовать5–10% head-sampling с deterministic parent policy; public sampled header не разрешает клиенту обход budget. Ошибки всегда в sanitized logs; sampling не гарантирует trace каждого error. Если нужны все slow/error traces — отдельный bounded tail sampler и routing/session budget, а не утверждение о head sampling. Retention первоначально log7d/trace3d/metrics15d с **жёстким size cap**, после замера объёмов согласовать; числа — настройки пилота, не production guarantees. Инфраструктура private/loopback, ops-auth, TLS по среде; Grafana не общедоступный путь к данным пользовательского API.

**Низкая cardinality:** labels service/env/level/static route/method/status class/job type/queue class. trace_id/span_id/http_request_id/job_id/run_id/well_id/actor/model hash не Loki labels/Prometheus labels; trace links и opaque IDs — structured metadata/trace attrs с доступом. [Loki cardinality guidance](https://grafana.com/docs/loki/latest/get-started/labels/cardinality/).

**Полезные metrics:** HTTP/gRPC request/error count и duration histograms; worker active/queue wait/processing duration/retry/dead-letter counts по типу; age oldest ready job/outbox lag/artifact failures/lease expirations/late-fence rejects; ML in-flight/capacity saturation и peak process RSS; collection lag/error/accepted/rejected/duplicate aggregate. Не вешать well_id на метрику и не выдавать model accuracy из `/ml/metrics` за health. Job progress — реальные persisted processed/total/stage через scoped job API, не придуманный процент CatBoost. Первая Dashboard покрывает один check path и зависимость Data/ML/PG; resource/QPS/retention tuning только после representative measurements.

O2 DoD: первый и повторный вызов существующего period check имеют реальные Go/Python/PG spans и log→trace link; Data span — только на фактически выполненном HTTP leg выбранной fixture либо в отдельном collector→Data→PG operation. Это не cold/warm benchmark и не обещание полного cache reset; секрет/телеметрия sentinel отсутствует в logs/spans/export; неизвестные headers не меняют scope; Collector/Loki/Tempo down/queue overflow/disk cap не ломают business result, drops видны; restart/rotation на Docker Desktop не обещает lossless; нет систематического двойного сбора одного app event через OTLP и stdout tail, но transport retry duplicates возможны — exactly-once telemetry не обещается; clean-install pin compatibility+resource/volume budget evidence. Только после этого считать common logging реально централизованным.

## 4. RabbitMQ и Kafka: выбор по настоящим workloads

| Workload | Требуемая семантика | Рекомендация |
|---|---|---|
| File-check / импорт | Ограниченное число тяжёлых заданий, retry/lease/cancel, результат в PG, per-job backpressure | RabbitMQ work queues/quorum + PG job state; импорт отдельно от check и с batch idempotency |
| Cohort100 bulk | Один замороженный input manifest/bundle/as_of, checkpoints/100 terminal outcomes, защита от двух finalizers | Тот же RabbitMQ transport после durable claim/fencing; сам broker не заменяет PG scope/lock/state |
| Notifications/внешняя доставка | Коммит события→delivery intent, retry/attempt ledger, dedupe/read отдельно review | Тот же broker при необходимости async delivery; in-app read projection/read-state сами по себе его не требуют |
| Retained telemetry replay / многие независимые consumers | Длительный event log, offsets/переигрывание, partition key/order/schema/retention | Kafka имеет естественную пользу; решение после объёмов/replay windows/операционной ответственности, не из одного масштаба100 |

**Выбор для первого queue slice — RabbitMQ**, один broker/client в Go worker, Python ML остаётся gRPC вычислителем без AMQP client. Причины: сейчас нужны job acknowledgements/retries/backpressure и PG effects, а не новый телеметрический журнал; меньше новых client seams. Это инженерная рекомендация для согласования, не измеренный throughput winner и не заявление, что Kafka не умеет tasks.

**Актуальная поправка:** Kafka4.2 объявила Queues/Share Groups production-ready; устаревшее противопоставление «Kafka только log, RabbitMQ только queue» неверно. Совместимость требуемого share protocol с конкретными Go/Python clients/versions **не проверена**; pin/client feature/failover test — отдельный gate, если выбрана Kafka. [Kafka4.2 release](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/), [upgrade notes](https://kafka.apache.org/42/getting-started/upgrade/). Kafka consumer/transaction guarantees не дают автоматически exactly-once effects во внешней PG; нужно coordinated/idempotent persistence. [Kafka design](https://kafka.apache.org/design/).

RabbitMQ: publisher confirms и consumer ack решают разные участки; confirm не означает, что PG-result сохранён. Использовать durable declarations/persistent messages, routing validation+mandatory returns и подтвердившийся publish; quorum HA требует majority нескольких реально размещённых nodes. Один local broker — **не HA/RPO**. [Confirms/acks](https://www.rabbitmq.com/docs/confirms), [reliability](https://www.rabbitmq.com/docs/reliability), [quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

Dead-letter transfer **не lossless по умолчанию**: quorum at-least-once dead-lettering требует явных поддерживаемых policy/overflow reject-publish/DLX conditions; иначе defaults могут потерять transfer. Сохранённый failed/dead-letter job в PG и reconciliation нужны независимо от DLQ availability. Условия и ограничения — [quorum dead lettering](https://www.rabbitmq.com/docs/quorum-queues#dead-lettering). Не ставить Kafka и RabbitMQ одновременно «на будущее».

## 5. Q0: долговечный input до брокерного исполнения

**Hard dependency:** нынешний hash/partial provenance не даёт входа для повторного вычисления. Job должен ссылаться на **immutable canonical CSV + raw input при его использовании + parse/mapping/timezone/recipe options + as_of/cohort manifest + доступный точный model bundle/policy**. Повтор не читает изменившуюся живую телеметрию, новый metadata справочник или current bundle cache. Нужны input availability/digest/ACL/size/retention и потеря артефакта как явный failed code. Одного model_version столбца или сверки response hash после вычисления недостаточно.

Минимальная рекомендация bounded file Q1 — **ArtifactStore поверх существующей PG** (content/manifest tables, bytes BYTEA/ограниченное compression и digest). При умеренных файлах это позволяет raw+canonical+options+job+outbox принять в одной транзакции, не добавляя обязательный MinIO. Размер/IO/backup cost измерить на выбранных20/50MiB limits до расширения; PG не объявляется подходящей для бесконечного архива. Предлагаемые начальные per-job bounds: raw≤20MiB, canonical model input≤50MiB без учёта compression, rows≤100000; raw50MiB вариант требует отдельного D1 решения. Общая bytes quota, max active jobs и terminal input TTL обязательны в enablement contract: без них durable admission не включать. Предлагаемая pilot policy — очистка terminal input в пределах24h после terminal только при отсутствии active/retained references; срок/quotas закрепляются до Q enablement, это не принятый SLA. Активные/retained retry inputs не удаляются по истёкшему terminal TTL; orphan/terminal GC не трогает saved result/review. Status/list queries читают только metadata, не BYTEA payload. Закрытые bytes доступны worker/backend по authorization, не публичному SQL/документам/брокеру. New input retention — явно согласуемая политика, а не скрытая смена нынешнего «bytes не архивируются».

Альтернатива object store: staged immutable PUT→verify digest/size→PG job+manifest/outbox commit; object/PG transaction не атомарны. Orphan/partial uploads имеют GC grace/reconcile, active jobs/retained manifests защищены от удаления, missing object проверяется до ML. Credentials, bucket/path/presigned URL не помещать в message. Удалять terminal artifacts только после принятой retention/backup policy; retries/review/history не ломать. Хранение inputs само по себе не меняет старую provenance partial на complete; complete требует code/runtime/bundle/input availability и проверенного replay.

**Bundle pin — до первой попытки:** immutable registry/ref полного bundle (model+meta+calibrator+normalizer+drift/feature recipe), доступность exact artifacts, approved policy hash. ML execution contract должен уметь потребовать expected bundle/version/rule и отклонить missing/mismatch **до predict**, без fallback current. Потребуется узкое additive execution-constraint расширение Upload/first chunk в contracts либо эквивалентный проверяемый pinned deployment adapter. Это не новая модель/promotion. Current dynamic Upload cache не становится pinned от job DB колонки; until gate закрыт durable retry с обещанием того же расчёта не включать.

## 6. Q1: первое durable job — file-check, не миграция всех задач

Два процесса из существующего Go backend: HTTP API — прием/чтение, `cmd/worker` — claim/вызов existing gRPC/persist. Это выделение исполнения ради restart/backpressure; domain/service modules остаются общими, не копируются. Durable queue message содержит opaque job_id, schema_version, dispatch_generation и ограниченный trace context/link; **не**50MiB bytes, credentials, user claims, свободные options или storage path. PG — источник истины, payload не даёт прав.

**Минимальные additive tables/interfaces (точные names/migration number после approval):**

- job: UUID/type/profile/cohort_version/subject refs/server actor, scoped request_id+fingerprint, input_manifest_id/bundle ref, state/stage/deadline/next_attempt, attempt_no/fence/lease_owner/lease_until, nullable result ref и safe failure code; unique(dedupe_scope,request_id), explicit typed states.
- outbox: unique message_id(job_id,dispatch_generation), pending/publishing/confirmed/next-attempt, bounded dispatch lease. В той же transaction, что принятый job или durable retry intent.
- inbox/attempt ledger: message/attempt outcome, claim/fencing и terminal dedupe; наличия строки received недостаточно, чтобы считать effects завершёнными.
- artifact/manifest и result relation; existing ManualCheck/UNIQUE/run_snapshot/review остаются финальными business records, не копируются в message broker.

Create: server scope/role/input validations→persist immutable artifacts+job+outbox→commit→**новый opt-in async endpoint** возвращает202 с job_id/Location. Retry того же request key возвращает существующий job/result, другой fingerprint409. Existing sync `/checks`, raw `/ml/upload` и bulk refresh не меняют response shape/поведение под видом feature flag. Перед UI switch согласовать F2 limits/форматы/check-vs-ingest из roadmap.

Publish: short outbox claim, publish mandatory persistent message, обработать unroutable return и confirm; только затем mark confirmed. Crash после broker confirm до PG mark даёт duplicate — допустим. Не держать database transaction до broker/network timeout. Broker down оставляет durable pending outbox; admission limits не позволяют бесконечный рост.

Consume: lookup job in PG→проверить execution rights/captured cohort и server-owned constraints→short atomic claim с новым fence/lease→immutable inputs+bundle validation→gRPC Upload→atomic ManualCheck/result link+job terminal+inbox completion→manual ack. Worker restart/ack loss вызывает redelivery; terminal job безопасно ack без повторного business effect. Active duplicate не запускает второй inference: defer/durable reconciliation по lease, не считать received message завершённой работой. Все переходы/result commit используют CAS(job_id,attempt/fence,lease owner,state), late старый worker не может завершить новую попытку. Trace/meta в queue не заменяет эти проверки.

Transient unavailable/rate limits — bounded backoff+jitter/attempt/deadline; invalid file/unsupported recipe/permission failure не крутятся бесконечно. Retry создаёт durable next-attempt/outbox **до** ack исходной delivery; broker DLQ — диагностический transport, PG сохраняет terminal failed/dead-letter status. Reconciler восстанавливает expired leases/stuck publishing/неопубликованные ready jobs и missing input/bundle, не делает replay с новым входом. Повтор operator допустим только явным retry с прежним input/constraints либо новой operation identity, с access/audit.

Backpressure: admission quota по типу/пользователю/входному объёму, очередь/max-inflight/prefetch/worker count bounded; overload429/503 с safe retry hint, без потери уже принятого job. Initial candidate — worker concurrency1/prefetch1 для тяжёлого ML, затем measured tuning; имеющиеся4threads/max16 RPC не являются доказательством нужной capacity. Не блокировать request short auth/read за всей ML очередью. Queue metrics не имеют job-id labels.

Cancel: explicit POST job/cancel после role/scope, queued job→cancelled; running→cancel_requested с fence invalidation/late-write guard. Client timeout/navigation не означает отмену. Deadline/cancel не гарантирует физическое прерывание CatBoost; завершившийся поздно результат не становится публичным success. Final commit атомарно проверяет актуальный fence/state/deadline/cancel; replay не воскрешает cancelled job. Progress API показывает stage/processed totals/attempt и saved result link, не fake percentage/ETA.

Для async trace worker attempt начинает новый bounded trace со Span Link к accept/publish context, а не бесконечный HTTP trace на часы. Request/job/attempt IDs связывают logs и PG. Job read/cancel/result после scope change проверяются server guard; disabled/чужой пользователь не получает output/artifact refs. Public error sanitized, internal diagnostic details доступны ops. Correlation-ID не даёт доступ к trace UI.

Q1 DoD: lost publish/confirm/ack, duplicate/reorder, crash до claim/во время ML/после result commit, PG rollback, broker unavailable/disk cap, expiry/retry exhausted/DLQ unavailable, changed/missing bundle/input, cancellation vs late completion, scope revocation, concurrent same-key/different-body409. Для успешно завершённого задания существует не более одного committed ManualCheck/result; у failed/cancelled задания результата может не быть, повторные вычисления возможны. Attempt/fence доказан PG integration, inputs/expected rule совпадают во всех попытках. Restart worker/broker не требует живого browser и не меняет сохранённый result. Ops retry path не обходит RBAC.

## 7. Q2: перенос bulk только с durable claim/fencing

Нельзя резервировать нынешний PostgreSQL session/advisory lock в HTTP и держать его всё время queued job. Нужен **durable active-job claim + fencing**; существующий lock может оставаться на ограниченном legacy/worker execution path на переходе, но единый coordinator исключает два active finalizers cohort между old/new modes. Claim на run scope атомарен, expiry увеличивает fence; завершение старого worker отклоняется даже если его ML call закончил позже. Блокировка одной очереди не является защитой cross-process PG writes.

При accept нового bulk request сохраняется profile/cohort_version/server actor/as_of и логическая attempt identity до подготовки входов. Политика различает durable принятую **намеренную работу** от готового frozen input: стадия capturing может законно завершиться error без ML result. До первого score materialize exact per-member canonical inputs, metadata/bindings, cohort100, feature/model/policy hashes и publish immutable manifest. Retry inference использует этот manifest, **не** повторный ReadApp на изменённой живой истории и не нынешний model cache. Bundle pin gate Q0 обязателен.

Member checkpoints unique(job_id,well_id,attempt/input identity) сохраняют actual scored/archived/inactive/insufficient/error; нет speculative full snapshot до100 terminal outcomes. По окончании100 — atomic full ml_run_snapshot+alerts/review linkage+job terminal; no partial global success. Attempt retries используют тот же вход/manifest, изменившееся membership/cohort или recipe — новая operation. Partial checkpoint не становится latest completed user snapshot. При failure prior completed result остаётся, новый failed/running attempt виден через accepted schema11 identity; raw errors не раскрываются.

Scheduler collection/import отдельно: source claim/watermark и CommitTelemetry уже атомарны, их нельзя заменить простым ack. Async import сначала explicit source batch/idempotency и допустимая duplicate policy; повтор не перезаписывает telemetry и не теряет watermark. Rabbit first slice не требует переносить все collection loops сразу. Kafka retained telemetry log — отдельная архитектурная стадия с volume/schema/replay обоснованием.
