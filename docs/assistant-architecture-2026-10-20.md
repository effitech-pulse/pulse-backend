## Решение и первые сценарии

Один модуль помощника внутри существующего Go backend, один всплывающий чат в SPA. Его interface принимает типизированное намерение и возвращает ссылку, уточнение либо подготовленный результат. Внешний seam распознавания языка не получает SQL, произвольные URL или право запускать операции. Leverage — общий исполнитель для диалога и формы; locality — проверки параметров, scope и материализация результата в одном месте. Deletion test: удаление этого модуля распределило бы проверки и согласованность просмотра/скачивания по клиентам. Тонкую обёртку над каждым endpoint отдельно не вводим.

| Сценарий | Первый результат | Ограничения |
|---|---|---|
| «Где посмотреть риски?» | `/ml-risk` — «Тревоги»; при явном контексте одной разрешённой скважины `/wells/{PulseID}?tab=overview` — «Риски» | Сам вопрос про отчёт не доказывает наличие отдельного отчёта по рискам. Не выбирать случайную скважину. |
| «Выгрузи реестр по текущим фильтрам» | Карточка параметров → «Сформировать» → число строк, дата формирования, просмотр и XLSX | Первый `report_type=wells_registry`. Нельзя добавить риск, период, график или PDF: текущий экспорт их не поддерживает. |
| «Покажи, как начать» | Знакомство: Скважины → пользователь выбирает скважину → Риски → Телеметрия → Проверки | Не создаёт проверку, не считает модель, не меняет заключение. При пустом фонде шаг выбора заменён объяснением отсутствия объектов. |

При «Составь отчёт» сначала спросить тип из доступного списка (пока один). При неподдержанном запросе, например «Риски за сентябрь в PDF», объяснить ограничение и предложить навигацию к рискам или реестр; замена только после явного выбора технолога. Названия и номера с неоднозначным соответствием требуют выбора разрешённого объекта, не угадывания ID. Вопросы помощника показывают уже распознанные значения и сохраняют их при уточнении.

## Точные параметры первого экспорта

Ни одно поле запроса не является разрешением доступа. Scope задаёт сервер; контекст клиента — только предлагаемые фильтры.

| Параметр | Допустимые значения и смысл | Предложенный default помощника |
|---|---|---|
| fund | `operational` / `presentation`; обычный API допускает пустое значение для всех разрешённых фондов | Обязательный конкретный фонд из текущего UI, показать источник; без контекста уточнить. Смешанный фонд в первом UI не предлагать. |
| archive | `current` / `archived` / `all` | Текущее значение списка, иначе `current`; архив независим от active. |
| active_only | bool; true — только active=true, false — оба состояния | Текущее значение списка, иначе false; false не означает «только неактивные». |
| ngdu / department | Необязательные int64 ID из разрешённых справочников; 0 не считать отсутствием | Текущие фильтры либо отсутствуют. Номер/название разрешать в ID с уточнением неоднозначности. |
| search | Подстрока номера скважины или ID Pulse, до 120 Unicode-символов | Текущий поиск либо пустая строка; внешние ID не подставлять. |
| sort | `id_asc`, `id_desc`, `name_asc`, `name_desc` | Текущий sort, иначе `id_asc`; равные имена упорядочиваются по ID. |
| format / columns | Только XLSX, фиксированная lifecycle-схема | Пользователь не редактирует набор полей; identity=pulse и lifecycle=true — технические константы исполнителя. |

Поля результата: `PULSE_ID, WELL_NUMBER, NGDU, CEX, ACTIVE, ARCHIVED_AT, RESPONSIBLE, REVISION`. Внешние UNITEK/ARMITS ID не добавлять. Просмотр использует эти же значения, null не заменяется нулём. Отсутствие даты/периода означает реестр на момент формирования, не историческое состояние на заданный день.

## Target: маленький interface и исполнение

Предлагаемые новые HTTP endpoints под `/api/v1/assistant` (не текущие маршруты):

- `GET /capabilities`: version, разрешённые intent/route/guide/report IDs и типизированные описания параметров. И UI, и распознавание используют один versioned allowlist. Это описание возможностей, не выгрузка объектов.
- `POST /resolve`: `{capabilities_version, text, context:{route_id, well_id?, registry_filters?}}` → discriminated union `clarification | navigation | report_draft | guide | unsupported`. Не формирует файл. Ссылку строит сервер/клиент по route_id и проверенному ID, а не из текста модели.
- `POST /results`: `{request_id, capabilities_version, report_type:"wells_registry", parameters}` → `ready {result_id, created_at, expires_at, parameters, columns, row_count, preview_rows, preview_limit, download_path}`. Пользователь нажал «Сформировать» после редактируемой карточки. Ответ — read-only результат; подтверждение не является правом изменить данные.
- `GET /results/{id}?offset=…&limit=…`: страницы тех же зафиксированных строк; `GET /results/{id}/download`: XLSX из тех же строк. `result_id` случайный opaque ID, не публичная bearer-ссылка. URL не содержит текст запроса/параметры чувствительных объектов.

Intent union: `navigate {route_id, well_id?}`, `prepare_report {report_type, parameters}`, `start_guide {guide_id}`. Не добавлять универсальный `execute {url,method,body}`, SQL, shell, внешнюю ссылку или произвольный tool name. Unknown fields/enums/несогласованная версия дают validation/refresh, не молчаливое игнорирование. Разрешённые route IDs в первом наборе: overview, structure, alerts, well.risks, well.telemetry, well.checks, well.history; guide_id=`first_steps_v1`.

Модуль `service` переиспользует Catalog.FilteredWells и XLSX adapter, не делает внутренний HTTP-запрос с привилегированным API key. Handler передаёт реальный principal/context. POST resolve/results надо явно добавить как read-only операции для viewer/technologist в local middleware; auth cookie/origin/CSRF действуют как у других POST. Авторизация отчёта соответствует существующему GET экспорта, не только роли создателя.

Prepared result: одна материализация разрешённых строк и XLSX, метаданные, scope/owner binding. Просмотр и файл читают её; изменения карточек после формирования не меняют уже показанные значения. На каждом чтении заново аутентифицировать пользователя, проверить владельца, текущие cohort membership и доступность всех входящих объектов по текущему состоянию. Также проверить права на сохранённые значения scope (например, старое NGDU), чтобы перенос объекта не раскрыл старую область новому пользователю. При потере доступа к любой строке закрыть весь результат с предложением сформировать заново; не отфильтровывать часть молча. Проверка пустого результата всё равно включает owner и текущий scope. Logout/смена пользователя удаляют клиентские черновики/результаты.

Минимальное хранение — ограниченный TTL cache в одном существующем процессе backend; без новой БД и таблиц. Связать opaque ID с текущей сессией и principal; для legacy без персонального account использовать отдельный серверный opaque session binding и честно сохранить ограничения shared-key профиля. Не выдавать результат по знанию одного ID. При рестарте/истечении TTL ответ `expired` и «Сформировать заново». Для первого прототипа предложены TTL 10 минут, не более 5000 строк на результат, 8 MiB на результат и 64 MiB на cache; лимиты на пользователя/одновременную сборку и eviction обязательны. Это стартовые ограничения, не измеренная ёмкость. На превышении — явная ошибка/сужение фильтров, без обрезанного «готового» файла. Multi-instance deployment потребует отдельного решения общего result storage; до него результат не обещает пережить смену инстанса.

`request_id` обеспечивает повторную выдачу того же результата в пределах TTL/owner; тот же ID с другими параметрами даёт conflict. Повтор после expiry — новое явное формирование. Ограничить размер текста/контекста и длину диалога. Предложение deadlines: resolve до 8 с, materialization до 10 с, отмена по request context; при timeout показывать сохранённый черновик и «Повторить». Автоматическое повторение формирования не нужно. После публикации result материализация неизменяема. Ошибки `unsupported`, `clarification`, `forbidden/not_found`, `expired`, `busy`, `timeout` имеют отдельные UI-состояния; недоступность помощника не блокирует обычную навигацию/экспорт.

## Минимум без выбранного LLM и альтернативы

Рекомендуется сначала тот же interface с детерминированным распознаванием известных формулировок и кнопками выбора операции/параметров. Неизвестный свободный вопрос переводится в явный выбор, а не в догадку. Весь scope, подготовка и онбординг работают без LLM. Позже provider adapter может возвращать только кандидата typed intent; схема и серверная валидация остаются обязательными. Пока существует один распознаватель, не создавать универсальный framework провайдеров (one adapter — hypothetical seam); real seam появляется при добавлении второго adapter.

Отдельно поднятая local/self-hosted модель с собственным inference endpoint — допустимый целевой вариант по предложению пользователя. Backend обращается к ней по внутреннему HTTP(S) через ограниченный adapter распознавания; браузер не вызывает модель напрямую. Это deployment модели, а не новый бизнес-микросервис помощника: executor, auth и результаты остаются в Go backend. Модель/квантизация, GPU/CPU/RAM, конкурентность, стоимость эксплуатации и задержка — OPEN; локальный контур уменьшает внешнюю передачу, но сам по себе не решает изоляцию и авторизацию. Timeout модели возвращает доступный детерминированный выбор операций. Инфраструктура этой задачей не меняется.

LLM provider — OPEN. Во внешнюю модель не передавать телеметрию, строки реестра, секреты, имена/внешние ID и историю по умолчанию; даже свободный текст может содержать промысловые сведения, поэтому до выбора допустимого контура внешняя передача не включается. Инструкции из текста не могут расширить allowlist/доступ. Ответы по числам и файлы строит исполнитель, не генерация текста. Логи: request_id, intent/status/duration/число строк; без raw prompt/строк/файлов. Предлагаемая первая версия не хранит серверную историю разговоров.

Прямой LLM → HTTP/tools отклонён из-за произвольных действий и дублирования проверок. Чистый клиентский «чат + текущий export endpoint» дешевле, но два чтения не дают один неизменяемый просмотр/файл. Новый микросервис добавил бы отдельные deployment/auth/network/cache без подтверждённой нагрузки. Очередь/async jobs сейчас не обоснованы: реестр около 1000–1700 объектов, без пересчёта модели; нужны измерения до усложнения. Polars/DuckDB не применяются к этому Go registry/XLSX потоку: нет аналитической агрегации, технологию менять не требуется. Зависимости не добавляются и не обновляются; актуальность внешнего LLM SDK здесь не заявлена.

## UX-согласование и онбординг

Переданы designer точные фильтры, XLSX-поля, route/tab IDs и одинаковое право просмотра/выгрузки для read-ролей. Утверждено пользователем: вариант A «Напарник», плавающая кнопка только с иконкой справа снизу, без видимой надписи «Помощник»; по нажатию всплывающий чат открывается над кнопкой. Это заменяет прежнее предложение кнопки в шапке и закреплённой правой панели. Доступное имя кнопки для скринридера и клавиатурное управление сохраняются. Чат не перекрывает критичные тревоги; адаптацию к узкому экрану уточняет designer в рамках выбранного паттерна. Обновление Figma ведёт designer; этот документ не подтверждает синхронизацию макетов. Правка параметров готового результата создаёт новый draft/result, смена фонда не переписывает старый результат — его фонд остаётся явно виден. Проект UI: единый всплывающий чат с различимыми карточками ссылки, параметров, результата и шага знакомства; маскот мини-робот в каске не сообщает «готово» до ready. Выбран образ A «Напарник»; дизайнер владеет деталями рисунка, геометрией, темами и доступностью; подробные решения фиксируются в его спецификации. Не изображать онбординг как автоматический запуск проверки. Шаг ожидает реальное наличие DOM-цели; недоступная/неотрисованная цель пропускается с объяснением. Онбординг не зависит от LLM; versioned локальный guide registry. Выход, повтор, назад и отсутствие объектов — обязательные ветки.

## Приёмка будущей реализации

1. Две формулировки «Выгрузи реестр» приводят к одинаковому typed draft; запрос без фонда уточняется, текущие фильтры видны с источником. Исправление НГДУ не сбрасывает поиск/архив; неоднозначный объект не выбирается автоматически.
2. «Риск >80%, за сентябрь, PDF» не превращается в молчаливый XLSX и не запускает ML. Неизвестные поля/форматы/route IDs отвергаются; prompt injection не расширяет allowlist.
3. Viewer/technologist могут создавать результат чтения только в своём scope, admin остаётся внутри cohort. Подмена well ID, result ID, session или отозванное право не раскрывают строки/имена/файл. Проверить перенос NGDU и старые значения снимка.
4. После формирования изменить исходную карточку: просмотр и XLSX result сохраняют исходные строки, порядок, null/false/0 и revision. Новое формирование отражает изменение; экспорт не обрезается незаметно.
5. Повтор request_id с теми же параметрами возвращает тот же result; другой набор даёт conflict. TTL, restart, capacity и timeout дают честный статус и сохраняют черновик; никакого фиктивного ready.
6. Пустая выборка показывает ноль и поддержанный пустой XLSX с заголовками; не подставляет образцы. При просмотре частичных страниц отображаются total и размер preview.
7. Онбординг доступен клавиатурой, восстанавливает фокус, прерывается/повторяется и не запускает checks/score; при пустом фонде и отсутствии DOM-цели не указывает на чужую скважину. Обе темы/reduced motion/неперекрытие тревог проверяет designer.
8. На 100/1700/5000 репрезентативных строках и параллельных сессиях измерить p50/p95 времени, heap/RSS, размер XLSX и лимиты cache. Целевой бюджет materialization ≤10 с требует подтверждения; доказательств ускорения или необходимости async сейчас нет.

## Передача реализации после одобрения фазы

- AN-B / backend-middle: ownership backend typed assistant module, transport allowlist, scoped prepared results и OpenAPI. Вход — этот контракт и UX; критерии 1–6/8; SQL/DDL не менять.
